# Purpose

`nfr-discovery` は、機能要件だけでは後から漏れやすい **非機能要件（Non-Functional Requirements）を発見し、MVP時点で明文化する** ための Discovery Skill である。[[project-discovery]] の **Phase12（NFR Discovery）** を担う。

このスキルは **実装設計を行わない**。DB設計・インフラ構築・監視ツール導入・CI/CD実装といった具体実装には踏み込まない。担当するのは **非機能要件の「発見・意思決定・仮置き整理」** である。

[[risk-discovery]] が「何が起きたら失敗するか（動くか）」を扱うのに対し、nfr-discovery は **「どの水準で動き続ければよいか（どこまで作ればよいか）」** を扱う。両者は別軸である。

目的は、以下の9観点を **MVP段階で最低1回ずつ検討し、明文化する** ことである。

* **性能**（初期表示 / API応答 / 同時利用者 / ピーク / バッチ / 重い処理）
* **可用性**（稼働率 / 許容停止 / メンテ時間帯 / 障害時の最低機能 / 外部障害時の代替）
* **セキュリティ**（認証・認可 / 管理画面保護 / 個人情報 / 権限分離 / ログ禁止情報 / 秘密情報管理）
* **運用性**（管理画面 / 日次週次作業 / 問い合わせ / 障害検知 / 手動復旧 / データ修正）
* **保守性**（設定 vs コード変更 / 業種別・店舗別・顧客別差分 / 仕様変更に弱い箇所）
* **拡張性**（ユーザー / 店舗 / 業種 / 外部API / 管理者 / 多言語・地域展開）
* **バックアップ/復旧**（対象 / 頻度 / RTO / RPO / 誤削除復元 / 開発 vs 本番データ）
* **監視/ログ**（監視対象 / エラー / 操作 / AI生成 / 外部API失敗 / 通知先 / 保持期間）
* **コスト制約**（月額上限 / API利用料 / AI生成 / ストレージ / 画像・PDF / 将来増加リスク）

> nfr-discovery は **過剰設計と不足の両方を失敗とみなす**。MVP段階で「大規模アクセスに耐える」のような曖昧表現で終わらせない。不明点は止めずに分類して記録する。**実装者が「どこまで作ればよいか」を判断できる状態** をゴールとする。

# When to use

主に **以下の Phase が完了した後** に実行する。利用規模・データ種類・外部依存・運営体制・リスクが整理された後でなければ、非機能要件を接地できない。

* [[requirements-discovery]]（Phase2）— 機能・業務フロー
* [[data-discovery]]（Phase9）— 扱うデータ種類 / 個人情報 / 保持
* [[integration-discovery]]（Phase10）— 外部依存 / 失敗時対応
* [[operations-discovery]]（Phase6）— 運営体制 / 運営作業
* [[legal-discovery]]（Phase7）— 個人情報・保持期間の法務前提
* [[metrics-discovery]]（Phase11）— 想定ユーザー数 / KPI / 計測ログ
* [[risk-discovery]]（Phase8）— 可用性/性能/バックアップ/復旧へ渡されたリスク

**使う場面**

* 機能要件は固まったが、性能・可用性・セキュリティ・運用・コストの線が引けていないとき
* MVP公開前に「どこまで作ればよいか」の非機能ラインを確定したいとき
* バックアップ・ログ保持・障害時動作など、後から漏れやすい項目を明文化したいとき
* コスト爆発（AI生成 / ストレージ / API利用料）のリスクを早期に押さえたいとき

**使わない / 渡す先**

* 具体的なクラウド構成・DB設計・監視ツール導入・CI/CD実装 → **範囲外（行わない。設計・実装フェーズへ）**
* 「何が起きたら失敗するか」の事業・運営・外部依存リスク → [[risk-discovery]]
* SLA・返金・サポート範囲・責任範囲の契約論点 → [[contract-discovery]]

# Discovery targets

必ず発見すること。**セキュリティや性能に偏らず、以下9カテゴリを必ず一巡する**。各項目は **MVP最低ライン** と **将来理想ライン** を分けて書く。

### 1. 性能要件（performance）

* 初期表示速度（目標 / 体感許容）
* API応答時間
* 同時利用者数（想定 / ピーク）
* ピーク時間帯（曜日・時間・季節）
* バッチ処理時間（夜間集計・定期処理）
* 画像・PDF・AI生成など重い処理の扱い（同期 / 非同期 / 待たせ方）

### 2. 可用性要件（availability）

* 目標稼働率（例: 99% / ベストエフォート）
* 許容停止時間（事業上どこまで止まってよいか）
* メンテナンス時間帯（計画停止をどこに置けるか）
* 障害時に最低限使える機能（縮退運転で残すもの）
* 外部API障害時の代替動作（停止表示 / キャッシュ / 手動 / 後回し）

### 3. セキュリティ要件（security）

* 認証・認可（ログイン方式 / セッション / 多要素の要否）
* 管理画面保護（アクセス制限 / IP制限 / 権限）
* 個人情報保護（取得・保存・表示・マスキング）
* 権限分離（運営 / 管理者 / 一般 / スタッフ）
* ログに出してはいけない情報（PII / 決済 / トークン / パスワード）
* 外部連携の秘密情報管理（APIキー / トークンの保管・ローテーション方針）

### 4. 運用性（operability）

* 管理者が確認すべき画面（ダッシュボード / 一覧）
* 日次・週次の運用作業
* 問い合わせ対応に必要な情報・画面
* 障害検知（誰が・どう気づくか）
* 手動復旧手順（再実行 / 再送 / 切り戻し）
* データ修正手順（誤データの直し方・誰がやるか）

### 5. 保守性（maintainability）

* 設定で変えたい項目（運営者が触れる）
* コード変更が必要な項目（開発者対応）
* 業種別・店舗別・顧客別の差分管理（共通 vs 個別）
* 将来の仕様変更に弱い箇所（ハードコード・密結合になりやすい所）

### 6. 拡張性（scalability）

* ユーザー増加
* 店舗数増加
* 業種追加
* 外部API追加
* 管理者追加
* 多言語化・地域展開の可能性

### 7. バックアップ・復旧（backup-recovery）

* バックアップ対象（DB / 画像 / 生成物 / 設定）
* バックアップ頻度
* 復旧目標時間 RTO（どれだけ早く戻すか）
* 復旧目標時点 RPO（どこまでのデータを守るか）
* 誤削除時の復元方針（論理削除 / 世代保持 / 復元手順）
* 開発データと本番データの扱い（分離・コピー禁止・マスキング）

### 8. 監視・ログ（monitoring）

* 監視対象（死活 / エラー率 / 遅延 / コスト）
* エラーログ
* 操作ログ（誰が何をしたか）
* AI生成ログ（入力・出力・コスト）
* 外部API失敗ログ
* 通知先（誰に・どの経路で）
* ログ保持期間（法務・コストと整合）

### 9. コスト制約（cost-constraints）

* 月額上限
* API利用料
* AI生成コスト
* ストレージ
* 画像・PDF生成
* 将来増加時のコストリスク（ユーザー増・利用増で何が爆発するか）

### 横断: 分類とMVP/理想ライン

不明・未確定は止めずに分類して記録する。**MVP最低ライン** と **将来理想ライン** を必ず分ける。

* **決定** — 確定した非機能要件
* **保留** — 今は決めない（決める時期を書く）
* **仮置き** — 暫定値で進める（根拠と見直し条件を書く）
* **要確認** — 上流・ユーザー確認が必要（`open-questions.md` へ）
* **リスクあり** — 後から変更しにくい / コスト爆発 / ユーザー影響大（[[risk-discovery]] と接続）

# Question logic

質問は **「どこまで作ればよいか（非機能の線）を決める」** ために行う。具体的なクラウド構成・ミドルウェア採用の質問は禁止する。

一度に大量質問しない。[[discovery-planner]] と同じ思想で、常に **「次に決めるべき1問」だけ** を質問する。各回答は **決定 / 保留 / 仮置き / 要確認 / リスクあり** で返せる形にする。

**禁止例（実装・構成に踏み込む質問）**

* Kubernetes を使いますか
* Redis を入れますか
* CDN はどう構成しますか
* DBのインデックス設計はどうしますか

**許可例（非機能の線を決める質問）**

* 初期表示は何秒までなら許容できますか
* 何分まで止まってよいですか（許容停止時間）
* 個人情報のうちログに出してはいけないものは何ですか
* 誤削除されたデータはどこまで戻せる必要がありますか
* 月額のインフラ・API費用の上限はいくらですか

### 質問の優先順位

1. **本番運用に致命的なもの**（これが無いと公開できない）
2. **個人情報・決済・予約・通知に関わるもの**
3. **障害時にユーザー影響が大きいもの**（可用性・障害時動作）
4. **コスト爆発につながるもの**（AI生成・ストレージ・API利用料）
5. **後から変更しにくいもの**（権限分離・データ構造・保持方針）
6. **仮置きで進められるもの**（性能目標値の暫定値など）

> MVP段階では過剰な非機能要件にしない。「今すぐ必要な最低ライン」を優先し、「将来的に必要な理想ライン」は分けて記録する。

# Discovery loop

```text
入力成果物（requirements / data / integration / operations / metrics / risk / legal）を確認
 → 9観点（性能 / 可用性 / セキュリティ / 運用 / 保守 / 拡張 / バックアップ / 監視 / コスト）の現状を読む
 → metrics の想定利用規模 / data の個人情報・保持 / integration の外部依存 と照合（規模・PII・依存の接地）
 → [[discovery-planner]]: 次に決めるべき非機能の論点を1問に絞って質問（優先順位順・実装/構成は聞かない）
 → ユーザー回答（必ず停止して確認）
 → 該当 nfr ファイルを更新 / MVP最低ライン と 将来理想ライン を分けて記録
 → 分類（決定 / 保留 / 仮置き / 要確認 / リスクあり）を付与
 → 「リスクあり」「要確認」は risk-discovery / open-questions.md と接続
 → [[discovery-auditor]]: 過剰設計 / 不足 / 決定と仮置きの混同 / バックアップ・ログ保持の欠落 / risk・operations・integration との矛盾 を検出
 → 不足・矛盾を洗い出す（必要なら上流へ差し戻す）
 → nfr/ を更新 / decisions.md に決定・保留・仮置きを記録
 → Phase完了判定（確信度つき）
 → 完了後 設計・実装フェーズへ「どこまで作ればよいか」を引き渡し
```

# Handoff / 差し戻し

## Backward Handoff（差し戻し）

以下の場合は上流に差し戻す。差し戻し時は **質問を1つに絞る**。

| 状況 | 差し戻し先 |
|---|---|
| ユーザー数・利用頻度が不明で性能・拡張性を接地できない | [[scope-discovery]] / [[requirements-discovery]] |
| データ種類・個人情報が不明でセキュリティ・バックアップを接地できない | [[data-discovery]] / [[legal-discovery]] |
| 外部API依存が不明で可用性・障害時動作を接地できない | [[integration-discovery]] |
| 運用担当・運用時間が不明で運用性・監視通知先を接地できない | [[operations-discovery]] |
| 事業上の許容停止時間が不明で可用性目標を接地できない | [[project-discovery]] / [[risk-discovery]] |
| KPI計測に必要なログが不明で監視・ログを接地できない | [[metrics-discovery]] |

## Forward Handoff（引き渡し）

* **To 設計・実装フェーズ**: 確定した非機能の線（「どこまで作ればよいか」）。DB設計・インフラ構築・監視ツール導入・CI/CD実装はここで初めて行う（nfr-discovery では行わない）。
* **To [[risk-discovery]]**: 「リスクあり」と分類した非機能項目（コスト爆発 / 後から変更しにくい / 障害時影響大）を、発生可能性 × 影響度で再評価してもらう。
* **To [[contract-discovery]]**: 可用性目標・許容停止時間から導かれる SLA / 責任範囲の契約論点。
* **To [[discovery-auditor]]**: 過剰設計 / 不足 / 決定と仮置きの混同 / バックアップ・ログ保持の欠落 / risk・operations・integration との矛盾の検出。

# Completion criteria

兄弟Skill共通の体裁だけでは「`セキュリティ` とだけ書いて完了」になりかねない。nfr は **性能・セキュリティに偏ってバックアップ・ログ・コスト・運用を見落としやすい** ので、nfr特有の完了条件を満たすこと（[Phase完了判定](#phase完了判定)を出す）。

* [ ] **MVPで最低限必要な非機能要件が明文化されている**
* [ ] **性能・可用性・セキュリティ・運用・保守・拡張・監視・バックアップ・コストが最低1回ずつ検討されている**
* [ ] **MVP最低ライン と 将来理想ライン が分かれている**
* [ ] **決定 / 保留 / 仮置き / 要確認 / リスクあり が混ざっていない**
* [ ] **実装者が「どこまで作ればよいか」を判断できる**
* [ ] **過剰設計と不足の両方がチェックされている**
* [ ] **バックアップとログ保持が記録されている**（忘れやすい two top）
* [ ] **セキュリティ要件が一般論で終わっていない**（ログ禁止情報 / 権限分離 / 秘密情報管理が具体）
* [ ] **「大規模アクセスに耐える」等の曖昧表現だけで終わっていない**
* [ ] **risk-discovery / operations-discovery / integration-discovery と矛盾していない**
* [ ] 不明点が `open-questions.md` に分離され、要確認として残っている

### Phase完了判定

```text
## Phase完了判定: NFR Discovery (Phase12)
- 性能: 検討済 / 不足
- 可用性: 検討済 / 不足
```

# Self-check

* [ ] 性能・セキュリティだけに偏っていないか
* [ ] **バックアップを忘れていないか**
* [ ] **ログ保持期間を忘れていないか**
* [ ] コスト制約（特にAI生成・ストレージ・画像/PDF）を忘れていないか
* [ ] 運用性（障害検知 / 手動復旧 / データ修正手順）を忘れていないか
* [ ] 9観点（性能 / 可用性 / セキュリティ / 運用 / 保守 / 拡張 / バックアップ / 監視 / コスト）を一巡したか
* [ ] MVP最低ライン と 将来理想ライン を分けたか
* [ ] 決定 / 保留 / 仮置き / 要確認 / リスクあり が混ざっていないか
* [ ] セキュリティ要件を一般論で終わらせず、ログ禁止情報・権限分離・秘密情報管理まで具体化したか
* [ ] 「大規模アクセスに耐える」のような曖昧表現だけで終わっていないか
* [ ] MVPに不要なエンタープライズ要件を押し付けていないか（過剰設計チェック）
* [ ] 実装者が「どこまで作ればよいか」を判断できる状態か（不足チェック）
* [ ] 具体的なクラウド構成・Kubernetes・microservices・Redis・queue・CDN を必要性なく採用していないか
* [ ] risk / operations / integration と矛盾していないか
* [ ] 最初は一問だけ・優先順位順に質問したか（大量質問していないか）

# Prohibited

この Skill では以下を行わない。nfr-discovery は **「非機能要件の発見・意思決定・仮置き整理」** に集中する。

* DB設計（テーブル / カラム / インデックス / ER図）
* インフラ構築・具体的なクラウド構成の決定
* 監視ツールの導入・設定
* CI/CD の実装
* Kubernetes / microservices / Redis / queue / CDN を **必要性なく採用すること**
* 「大規模アクセスに耐える」など **曖昧な表現だけで終わらせること**
* セキュリティ要件を **一般論だけで終わらせること**（ログ禁止情報・権限分離・秘密情報管理を具体化する）
* **バックアップとログ保持を忘れること**
* MVPに不要な **エンタープライズ要件を押し付けること**
* 「何が起きたら失敗するか」の事業・運営リスクの確定（→ [[risk-discovery]]）
* SLA・返金・サポート範囲・責任範囲の確定（→ [[contract-discovery]]）
