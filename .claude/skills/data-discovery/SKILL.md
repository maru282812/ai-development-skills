# Purpose

このスキルは **DB設計を行うためのスキルではない**。目的は、サービスが扱う **情報そのもの** を発見すること。

- どんな情報を扱うのか
- どこから取得するのか / どこで作成されるのか
- 誰が更新するのか
- どう流れるのか（生成 → 通過 → 保存 → 外部送出）
- いつ削除されるのか / どれだけ保持するのか
- 他システムとどう連携するのか / どこまで自システムの責任か

画面・機能・運営・法務・リスクを検討した結果、「そもそも何のデータを扱うサービスなのか」が曖昧なまま実装へ進むことを防ぐ。**まず情報を発見する。実装方法は決めない。**

[[project-discovery]] の Phase9 を担う。ここが抜けると下流（[[legal-discovery]] / [[risk-discovery]]）で事故るため、実装優先度は高い。

# 基本方針

- DB / テーブル / カラム / ER図 / API / 技術選定 / インフラは設計しない（[禁止事項](#禁止事項)）。情報の発見と責任の明確化に徹する。
- 1サイクル＝1テーマ。複数のデータ領域を同時に質問しない（[深掘り質問ルール](#深掘り質問ルール)）。深掘りの1問は [[discovery-planner]] が作る。
- 法的判断はしない。個人情報は **対象データの抽出のみ** 行い、判断は [[legal-discovery]] へ渡す。
- 不明点を勝手に確定しない。`decisions.md` に **保留 / 仮置き(assumption)** として登録する（[意思決定の記録](#意思決定の記録)）。
- 既存コード / DB / API / UI には一切変更を加えない（探索と文書化のみ）。

# 入力

- `requirements/requirements.md`（[[requirements-discovery]] の成果物）
- `decisions.md`（[[project-discovery]] の決定ログ）
- `business/business-model.md`（[[business-discovery]] / 存在する場合）
- `operations/operations.md`（[[operations-discovery]] / 存在する場合）
- `legal/legal.md`（[[legal-discovery]] / 存在する場合）
- `risk/risk.md`（[[risk-discovery]] / 存在する場合）

> 未実装フェーズの入力が無い場合は、その前提を `assumption` として置き、`open-questions.md` に積む。捏造しない。

# 出力

- `data/data.md`

# 発見対象

## 1. 管理対象データ（永続）
サービス内で永続化されるデータ。例: ユーザー / 店舗 / 商品 / 予約 / 決済 / 投稿 / メッセージ / アンケート / 問診票。

## 2. 一時データ（非永続）
永続保存しないデータ。例: セッション / 検索条件 / フィルタ / 下書き / キャッシュ。

## 3. 外部データ
自システムが所有しないデータ。例: Google / LINE / Stripe / Hotpepper / Instagram / Shopify。

## 4. データ生成元
その情報はどこから生まれるか。例: ユーザー入力 / 管理者入力 / API取得 / AI生成 / システム計算。

## 5. 更新責任者
誰が変更できるか。例: ユーザー / 管理者 / 自動処理 / 外部サービス。

## 6. データの流れ（フロー）【補完】
各データが **どこで生まれ → どこを通り → どこに保存され → どこへ出ていくか** を概念レベルで整理する。実装経路ではなく情報の移動を捉える。詳細なフロー図化が必要なら [[data-flow-mapper]] へ渡す。

## 7. ライフサイクル
作成 / 更新 / 参照 / アーカイブ / 削除 される条件を整理する。

## 8. 保持期間・削除・エクスポート【補完】
- **保持期間（retention）**: いつまで持つか / 自動失効するか
- **削除**: 論理削除か物理削除か / ユーザー起点の削除要求に応じるか
- **エクスポート/ポータビリティ**: ユーザーが自分のデータを取り出せる必要があるか（[[legal-discovery]] の前提）

## 9. データ所有権【補完】
そのデータは誰のものか（ユーザー本人 / 事業者 / 共同）。退会・移管・第三者提供時の扱いの前提になる。[[legal-discovery]] / [[risk-discovery]] へ渡す。

## 10. 概念的な関連【補完・ER設計はしない】
「ユーザーは複数の予約を持つ」「予約は1つの店舗に属する」程度の **概念的な所有・参照関係** のみ。カーディナリティの厳密化・正規化・ER図は **やらない**（後工程）。

## 11. データの重要度
Critical / Important / Optional に分類し、重要度を定義する。消失・改ざん時の影響度の目安になる。

## 12. 個人情報判定（抽出のみ）
氏名 / 電話番号 / メール / 住所 / LINE ID / 予約履歴 / 決済情報 などを抽出する。**法的判断はしない**。対象データを洗い出し、[[legal-discovery]] / [[risk-discovery]] で利用する。

## 13. データ量・更新頻度の概算【補完】
件数のオーダー（数百 / 数万 / 数百万）と増加ペース、更新頻度の目安。厳密値でなくよい。[[nfr-discovery]] の入力。

## 14. 計測可能イベント【補完】
どの状態変化が計測対象になりうるか（登録・予約確定・決済完了・解約など）。[[metrics-discovery]] の入力。

## 15. システム境界
どこまでが自システムの責任か。例（予約システム）: 自システム = 顧客 / 予約情報、外部 = Stripe決済 / LINE通知。

# 進め方（Discovery ループ）

```text
入力整理
 → [[discovery-planner]]: 次に発見すべき1データ領域に絞って質問（1テーマ1問）
 → ユーザー回答（必ず停止して確認）
 → data/data.md を更新 / decisions.md に決定・保留・仮置きを記録
 → Phase完了判定（確信度つき）
 → 全領域カバー後 [[discovery-auditor]] へ（横断監査・矛盾検出）
 → 差し戻し or 後続フェーズへ引き渡し
```

## 深掘り質問ルール

1回で1テーマのみ。複数のデータ領域を同時に質問しない。

- 悪い例: 「ユーザー情報は？ 決済情報は？ 通知履歴は？」
- 良い例: 「ユーザーに関して保存したい情報は何ですか？」

# 意思決定の記録

発見した各データ項目は `decisions.md` に区分して記録する（[[project-discovery]] の決定ログ機構）。

- **決定(decision)**: ユーザーが確定した内容。
- **保留(pending)**: 決める必要があるが未決 → `open-questions.md` へ。
- **仮置き(assumption)**: AI/暫定で置いた前提。**確定ではない**。下流（legal/risk/scope/実装）へ渡る前に必ず昇格 or 解消する。

# 差し戻しループ（再入可能性）

このフェーズの発見は前段・後段を更新する。検出したら該当 `decisions.md` を更新し、影響フェーズを再オープンする。

- PII を新たに発見 → [[legal-discovery]] / [[risk-discovery]] を差し戻し
- 保持期間が決まる → [[legal-discovery]] を更新
- 外部データを発見 → [[integration-discovery]] を更新
- データ量が想定外 → [[nfr-discovery]] を更新

# 禁止事項

- DBテーブル設計 / カラム設計 / ER図作成
- API設計 / 技術選定 / インフラ設計

これらは後工程の担当。このスキルは情報の発見に徹する。

# 完了条件

以下が説明できる状態になったら完了（[Phase完了判定](#phase完了判定)を出す）。

- 何のデータを扱うか
- 誰が作るか / 誰が更新するか
- どこから取得するか / どう流れるか
- どこまで保存するか（保持期間・削除・所有権）
- どこまで自システム責任か
- どれが個人情報か（抽出済み）

不明点が残る場合は `decisions.md` に保留 / 仮置きとして登録する。未昇格の仮置きが残る間は「完了」にしない。

## Phase完了判定

```text
## Phase完了判定: Phase9 Data Discovery
- データ領域カバー率: <x/y>
- 個人情報の抽出: 完了 / 未完了
- 未解消の保留: <件数>
- 未昇格の仮置き(assumption): <件数>
- 確信度: 高 / 中 / 低
- 判定: 完了 / 継続 / 差し戻し（→ どのPhaseへ）
```

# セルフチェック

- DB / カラム / ER図 / API / インフラに踏み込んでいないか（情報の発見に留めたか）
- 1テーマ1問になっているか（複数データ領域を同時に質問していないか）
- 個人情報を「抽出」だけして、法的判断をしていないか
- 保持期間 / 削除 / 所有権 / データの流れを発見したか（補完項目を飛ばしていないか）
- 不明点を `decisions.md` に保留 / 仮置きとして登録したか（勝手に確定していないか）
- 後段の発見で前段（legal/risk/integration/nfr）を差し戻したか
- 後続フェーズへ「全部」でなく必要情報だけ抽出して渡したか
- 既存コード / DB / API / UI に変更を加えていないか
