# Purpose

アプリに組み込む LLM プロンプトを、目的・出力仕様・評価方法まで含めて設計する。
「なんとなく書いたプロンプト」を、変更に強く品質を測定できる構造化プロンプトにする。

対象:
- system prompt(役割・制約の定義)
- タスクプロンプト(分析・要約・抽出・インタビュー進行など)
- 出力フォーマット指定(JSON スキーマ、構造化出力)
- プロンプトテンプレート(変数埋め込み型)

# When To Use

- 新しい AI 機能のプロンプトをゼロから設計したい
- 既存プロンプトの出力品質が不安定で改善したい
- 出力形式(JSON等)が守られないのを直したい
- プロンプトをテンプレート化・パッケージ化したい

プロンプトを DB に保存する機能の設計は [db-designer](../db-designer/skill.md)、
AI 呼び出し API の設計は [api-designer](../api-designer/skill.md) を使う。

# Procedure

### 1. 目的と成功条件の確定

- このプロンプトは**何を入力に何を出力する**のか、1文で定義する
- 「良い出力」「悪い出力」の具体例を最低1つずつ確認する(ユーザーから引き出す)
- 出力の用途を確認する: 人がそのまま読む / プログラムでパースする / 次の LLM 呼び出しに渡す
  → パース用途なら構造化出力(JSON)が必須

### 2. 現状分析(改善の場合)

- 既存プロンプトの全文と、実際の失敗出力例を入手する
- 失敗を分類する: 形式違反 / 内容の質 / 指示の無視 / 長さ / トーン / hallucination
- プロンプト起因か、入力データ起因か、モデル選定起因かを切り分ける

### 3. 構造設計

以下のブロック構成で組み立てる(不要なブロックは省く):

1. **役割**: 「あなたは〜」は1〜2文で具体的に(肩書きより行動基準を書く)
2. **タスク**: 何をするか。手順が複数あるなら番号付きで
3. **制約**: してはいけないこと。理由も添える(理由があると遵守率が上がる)
4. **入力データ**: XMLタグ等で本文と明確に区切る(`<input>...</input>`)
5. **出力形式**: スキーマ・例を明示。「JSONのみ、説明文なし」を明記
6. **few-shot 例**: 出力が安定しない場合のみ追加(1〜3例。例は多様性を持たせる)

設計原則:
- 指示は「〜しない」より「〜する」で書く(否定形は守られにくい)
- 1プロンプトに複数の異質なタスクを詰めない(品質が落ちるなら呼び出しを分割)
- 変数埋め込み部分(ユーザー入力)は区切り文字で囲み、プロンプトインジェクション耐性を持たせる
- 日本語出力が必要なら明示する(入力が英語混じりだと英語で返ることがある)

### 4. 出力フォーマット設計(構造化出力の場合)

- JSON スキーマを定義し、各フィールドの型・必須/任意・取りうる値を明記する
- パース側(zod スキーマ等)とプロンプト内の指示を**完全一致**させる
- 失敗時のリトライ・フォールバック方針も提案する(パース失敗→1回再試行 等)

### 5. 評価方法の設計

- テスト入力を 3〜5 ケース用意する(典型 / 端 / 空・短い入力 / 攻撃的入力)
- 各ケースの期待出力(または合格基準)を定義する
- 改善時は**変更前後で同じテストケースを通して**比較する(1度に変える要素は1つ)

### 6. 納品

- 完成プロンプト全文(変数部分は `{{variable}}` 形式で明示)
- 設計意図の説明(各ブロックがなぜその書き方か)
- テストケースと評価基準

# Output Template

```md
# プロンプト設計: <機能名>

## 目的
(入力 → 出力 を1文で)

## 完成プロンプト
\```
(全文。変数は {{variable}})
\```

## 変数一覧
| 変数 | 内容 | 由来(どのテーブル/入力) |
|---|---|---|

## 出力スキーマ
\```json
(JSON出力の場合)
\```

## 設計意図
- (主要な設計判断とその理由)

## テストケース
| # | 入力 | 期待出力/合格基準 |
|---|---|---|

## 運用上の注意
- (モデル変更時の再テスト、コスト、レイテンシ等)
```
