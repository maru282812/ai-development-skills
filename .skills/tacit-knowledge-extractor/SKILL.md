# Purpose

「知っているのに書けていない」知識を、質問設計によって引き出し、構造化する。
暗黙知は「まとめて書いて」と頼んでも出てこない——本人には当たり前すぎて、
何が知識なのか自覚がないから。だから**具体例から始めて一般化する**方向で掘る。

抽出した知識は、discovery 工程・営業資料・引き継ぎ・プロンプト設計の入力として再利用できる。
セッションを跨いで使える形（ファイル）に必ず落とす。

# When To Use

- 業務経験・接客経験・現場の勘を、資料・要件・プロンプトの材料にしたい
- 「自分だけができる」状態の作業を、他人（またはAI）に渡せる形にしたい
- ドメインの前提知識（業界の慣習・顧客の本音・地雷）を明文化したい
- [project-discovery](../project-discovery/SKILL.md) を始める前に、ユーザーの業界知識を先に吐き出させたい

要件そのものの洗い出しは [requirements-discovery](../requirements-discovery/SKILL.md)、
事業として成立するかの整理は [business-discovery](../business-discovery/SKILL.md) を使う。

# Procedure

### 1. トピックと用途を確定する

- 何の知識を抽出するか（例: 美容室オーナーへの営業、獣医の受付業務の勘所）
- **抽出後に何に使うか**を確認する（要件の材料 / 営業資料 / 引き継ぎ / プロンプト）。
  用途によって掘る深さと構造が変わる

### 2. 具体例から始める（抽象論を最初に聞かない）

最初の質問は必ず実例:「最近あった実例を1つ、時系列で話してください」。
実例が出たら、その中の**判断の分岐点**に印を付けて掘り下げる
（「ここでAではなくBにしたのはなぜ?」）。

一問一答で消耗させない。[requirements-discovery](../requirements-discovery/SKILL.md) と同じく
**1回に3〜5問をまとめて**、表で答えられる形式にする。

### 3. 4方向で掘る

| 方向 | 質問の型 | 引き出せるもの |
|---|---|---|
| 一般化 | 「それは毎回そうする? どんな時に変える?」 | ルール・パターン |
| 例外 | 「そのやり方が通用しないのはどんな相手/状況?」 | エッジケース・地雷 |
| 判断基準 | 「AとBで迷ったら、最終的に何で決める?」 | 優先順位・価値基準 |
| 前提 | 「それを知らない新人は、まず何を間違える?」 | 暗黙の前提・業界常識 |

ユーザーの回答に**矛盾や曖昧さがあったら流さずに指摘して確認する**
（「さっきは○○と言っていたが、この場合は逆では?」）。矛盾の解消こそが暗黙知の核心であることが多い。

### 4. 構造化して書き出す

`domain-knowledge/<topic>.md` に生成する:

```md
# <トピック> 暗黙知ドキュメント

## この知識の用途
(何の入力として使うか)

## 用語集
| 用語 | 現場での意味（辞書的定義とのズレを含む） |

## 判断基準（if-then）
| 状況 | 判断 | 理由 |

## 例外・地雷
- <通用しないケース、やってはいけないこと、失敗談>

## 暗黙の前提（新人が間違えるポイント）
- ...

## 未言語化の残り（open questions）
- <掘り切れなかった論点。次回セッションの入口>
```

### 5. 本人検証で締める

生成した文書をユーザーに読ませて「違和感のある箇所」を指摘してもらう。
本人が「そうそう、でもここは違う」と言った箇所が最も価値が高い——修正して確定する。
未言語化の残りが多ければ、2回目のセッションを提案する。

# 実行モデルティア

推奨ティア: **deep**（良い質問の設計と矛盾の検出が抽出の質を決め、推論力に依存する）。
最上位推論クラスのモデルが使えない環境でも中止しない。代わりに劣化運転として、
1回のセッションで掘る方向を2つまでに絞り、一般化を急がず実例の記録に徹し、
「未言語化の残り」を多めに残して次回へ渡すこと。
具体的なモデル名はここに書かない（対応表は `.skills/MODEL-TIERS.md`）。
