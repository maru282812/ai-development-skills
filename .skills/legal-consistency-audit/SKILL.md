# Purpose

相互参照する法務文書群の矛盾検出は、人間が最も見落としやすく、横断読解が最も効く領域。
利用規約だけ読めば正しく、プライバシーポリシーだけ読んでも正しいのに、
**並べると矛盾している**——この種の事故を公開前・販売前に検出する。

原則:

- **read-only**: 文書を修正しない。指摘レポートを出して止まる
- **適法性を断定しない**: 検出するのは「文書間・文書と実態のズレ」。
  法的な正誤の最終判断は必ず専門家確認へ回す
- **指摘には出典を付ける**: どの文書のどの条項とどの条項が矛盾するか、引用で示す

# When To Use

- サービス公開前・販売前に法務文書一式を横断チェックしたい
- 課金方式・データ取扱い・提供範囲を変更した後、全文書に反映漏れがないか確認したい
- [legal-publication-manager](../legal-publication-manager/SKILL.md) で文書を配置した後の最終監査
- 雛形を流用して作った文書に、別サービスの記述が残っていないか確認したい

文書がまだ無い（何が必要かの段階）なら [legal-discovery](../legal-discovery/SKILL.md)、
契約条件そのものの整理なら [contract-discovery](../contract-discovery/SKILL.md) を使う。

# Procedure

### 1. 文書インベントリを作る

- 監査対象の文書を全て特定する: `legal/` 配下・実際の掲載ページ・雛形（`legal/templates/`）
- `legal/legal-doc-registry.md` があれば照合する:
  レジストリにあるのに実体が無い**幽霊文書**、実体があるのにレジストリに無い**野良文書**を検出
- 各文書の版・最終更新日を控える（後の軸7で使う）

### 2. 監査軸で横断チェックする

7つの軸で、全文書を突き合わせる。各軸で「文書A条項X vs 文書B条項Y」の形で矛盾を拾う:

1. **用語定義** — 同じ概念に別の語を使っていないか（「ユーザー」「会員」「利用者」）。
   同じ語に文書ごとに違う定義を与えていないか
2. **責任範囲・免責** — 免責の範囲が文書間で食い違わないか。
   規約では免責しているのに契約書では保証していないか
3. **データ取扱い** — 取得項目・利用目的・第三者提供・委託先・保持期間・削除手続が
   全文書で一致するか（プラポリ vs 規約 vs 同意文言 vs 委託契約）
4. **金銭** — 料金・支払時期・返金・解約・キャンセル条件が
   規約 / 特商法表記 / 画面表示で一致するか
5. **手続** — 通知方法・変更手続・問い合わせ窓口・準拠法・管轄裁判所のズレ
6. **実態との一致** — 文書の記載とアプリの実態を突合する:
   `data/data.md`（[data-discovery](../data-discovery/SKILL.md) 成果物）や実装・画面を確認し、
   「取得していると書いていないデータを実は取得している」
   「書いてある機能・窓口が実在しない」を検出する
7. **版・残留物** — 更新日の不整合、旧サービス名・旧料金・雛形のプレースホルダ
   （`<会社名>` 等）の残留

### 3. 重大度で分類する

- **Critical**: ユーザー・契約先に実害が出うる矛盾（データ取扱いの不一致、
  返金条件の食い違い、取得データの記載漏れ）。公開・販売前に解消必須
- **Major**: 解釈次第でトラブルになる曖昧さ・不一致
- **Minor**: 表記ゆれ・用語の不統一（実害は薄いが信頼性を下げる）

### 4. レポートを出して止まる

Output Template で報告し、文書は修正せず停止する。
Critical には修正方針の候補を添えるが、**法的判断を要するものは全て
「要専門家確認」タグを付け**、`legal/legal-open-questions.md` への追記を提案する。

```md
(同形式)

## 整合していた軸

## 次のアクション
- [ ] Critical を修正 → 再監査

```

# Dispatch 対応（受け側モード）

対象が[[dispatch-pattern-builder]]方式のスキル実行文（ID + API ベースURL）で渡された場合:

1. `GET /api/<resource>/{id}` で監査対象の文書一式を取得する
2. 上の Procedure で監査する（read-only 原則・専門家確認の原則は同じ）
3. 重大度別の指摘リストを `POST /api/<resource>/{id}/<writeback>` で書き戻し、status を進める（冪等）

実行文がない通常の依頼では、このセクションは無視してよい。

# 実行モデルティア

推奨ティア: **deep**（文書横断の矛盾検出は推論力への依存が最も大きい領域）。
最上位推論クラスのモデルが使えない環境でも中止しない。代わりに劣化運転として、
監査軸を1つずつ区切って実行してユーザー確認を挟み、網羅を断定せず
「上位モデルでの再監査を推奨」と明記すること。
具体的なモデル名はここに書かない（対応表は `.skills/MODEL-TIERS.md`）。
