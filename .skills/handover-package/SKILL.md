# Purpose

アプリの販売・譲渡時に、買い手が運用を引き継ぐために必要な情報を1つのパッケージに集約する。
discovery 成果物（operations / integration / legal）とリポジトリの実態をスキャンして生成するため、
「頭の中にしかない引き継ぎ情報」を作業ゼロで文書化できる。

**絶対原則: シークレットの値を成果物に書かない。**
環境変数はキー名・用途・取得場所（どのサービスのどの画面で再発行できるか）だけを書く。
`.env` 系ファイルは読まず、`.env.example` とコードからキー名を特定する。

# When To Use

- アプリを販売・譲渡・移管する準備を始めるとき
- 「引き継ぎに何が必要か」を洗い出したいとき
- 外部サービスの名義切替（Supabase / Vercel / LINE / Stripe / ドメイン等）の段取りを作るとき

アプリ内に運営者向け手順パネルを埋め込みたいなら [ops-guide-embedder](../ops-guide-embedder/SKILL.md)。
本スキルは逆に、販売時にそれを**剥がす**手順をパッケージに含める。

# Procedure

### 1. リポジトリをスキャンして実態を把握する

- `.env.example` / `.env.local.example` から環境変数のキー名を収集する
  （実 `.env` は読まない。存在する場合は「実ファイルあり・引き渡し時に値を別経路で渡す」とだけ記す）
- `package.json` の依存と import 文から外部サービス SDK を検出する
  （例: `@supabase/*`, `stripe`, `@line/bot-sdk`, `resend`, `openai` 等）
- `features/ops-guide/` の有無を確認する（あれば剥がし手順を 50-cleanup.md に含める）
- migration / seed に開発用・テスト用データ投入が無いか確認する

### 2. discovery 成果物を取り込む

存在するものだけ使う（無いものは 90-open-items.md に「未整備」として記録）:

- `operations/` — 日次・週次・月次の運用作業、問い合わせ対応フロー
- `integration/` — 外部サービスの契約者・アカウント名義・依存関係
- `legal/legal-doc-registry.md` — 法務文書の掲載状況・版
- `contract/` — 提供範囲・サポート条件（売買契約の参考情報として）

### 3. 名義切替手順を組み立てる

検出した外部サービスごとに「現在の名義 → 買い手名義への切替手順」を書く。
切替不能なサービス（譲渡を許さない規約等）は要確認として明示する。
順序に依存がある場合（例: ドメイン移管前に DNS 設定を控える）は番号付き手順にする。

### 4. handover/ 配下に生成する

| ファイル | 内容 |
|---|---|
| `00-overview.md` | 構成図・技術スタック・リポジトリ構成・引き渡し物リスト |
| `10-env-vars.md` | 環境変数: キー名 / 用途 / 取得場所（**値は書かない**） |
| `20-services.md` | 外部サービス一覧・現名義・料金プラン・名義切替手順 |
| `30-operations.md` | 運用手順（operations 成果物の要約＋リンク） |
| `40-legal-status.md` | 法務文書の掲載状況・版・要更新箇所（社名・連絡先の差し替え一覧） |
| `50-cleanup.md` | 引き渡し前の後始末: ops-guide 剥がし / テストデータ削除 / 開発者アカウント除去 |
| `90-open-items.md` | 未整備・要確認事項（買い手との交渉で決める事項を含む） |

### 5. 引き渡しチェックリストで締める

生成後、`00-overview.md` 冒頭に「引き渡し完了条件」のチェックリストを置く
（名義切替完了 / シークレット再発行 / cleanup 実施 / 法務文書の社名差し替え / 動作確認）。

### 6. セルフチェック

- 成果物のどこにもシークレット値・APIキー・パスワードが**書かれていない**か grep で確認する
- 買い手がこのパッケージ**だけ**を読んで運用開始できるか（会話の文脈に依存していないか）
- 法務文書の引き渡し後の適法性（社名・特商法表記の差し替え）が 40 に含まれているか。
  文書間の矛盾が疑われる場合は [legal-consistency-audit](../legal-consistency-audit/SKILL.md) を先に実行する

# 実行モデルティア

推奨ティア: **standard**（スキャン→集約→テンプレ生成の手順追従型のため標準クラスで品質が安定する）。
最上位推論クラスのモデルを占有する必要はない。売買条件・責任範囲など判断を要する論点が出たら、
その論点を明示して [contract-discovery](../contract-discovery/SKILL.md) /
[adversarial-review](../adversarial-review/SKILL.md) など deep ティアのスキルへ引き渡すこと。
具体的なモデル名はここに書かない（対応表は `.skills/MODEL-TIERS.md`）。
