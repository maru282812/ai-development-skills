# Purpose

アイデア・要望段階の機能を、SaaS プロダクトとして実装可能な仕様に整理する。

必ず扱う項目:

- ユーザー種別(エンドユーザー / 管理者 / 運営、テナント構造)
- 管理者導線(運営・テナント管理者が何をどの画面でやるか)
- エンドユーザー導線(主要ユースケースの画面遷移)
- MVP(最初のリリースで削れない最小範囲)
- Phase 分け(リリース単位の優先順位)
- 権限(誰が何をできるか)
- 課金 / プランの影響(プラン別の機能制限)
- 運用画面(運営側が必要とする管理・サポート機能)
- ログ / 監査(誰が何をしたかの記録要件)
- CSV / export(データ持ち出し要件)
- 通知(メール・アプリ内通知の要否)

# When To Use

- 要望・アイデアを実装可能な仕様に落としたい
- MVP の範囲を決めたい、優先順位を付けたい
- 管理画面側の仕様(運用に必要な機能)を漏れなく洗い出したい
- ユーザー種別ごとの導線・権限を整理したい
- 機能一覧・Phase 分けの形でロードマップ化したい

仕様が固まった後の実装計画は [implementation-planner](../implementation-planner/skill.md)、
画面単位の使い勝手の改善は [ui-ux-review](../ui-ux-review/skill.md) を使う。

# Procedure

### 1. 目的とユーザー価値の確認

- 「誰の・どんな課題を・どう解決するか」を1〜2文で言語化する
- 成功の判断基準(利用される状態とは何か)を確認する

### 2. ユーザー種別と権限の整理

- 関係するユーザー種別(エンドユーザー / テナント管理者 / 運営)を列挙する
- テナント構造(organization / project の階層)と、機能が属する階層を確認する
- 種別 × 操作の権限マトリクスを作る

### 3. 機能の洗い出し

- ユーザー向け機能だけでなく、[references/product.md](references/product.md) セクション1の
  「SaaSで漏れがちな機能チェックリスト」(運用画面・監査ログ・export・通知・プラン制限)を必ず通す
- 機能を一覧表にし、対象ユーザー種別を付ける

### 4. MVP の切り出し

- 「これがないと価値が成立しない」機能だけを MVP に残す
- 判断基準は [references/product.md](references/product.md) セクション2を参照
- 削った機能は「やらない」ではなく Phase 2 以降に置き、削った理由を書く

### 5. Phase 分けと優先順位

- MVP 以降を、価値の大きさ・依存関係・実装コストで Phase に並べる
- 各 Phase に「リリースするとユーザーが何をできるようになるか」を1行で付ける

### 6. 導線の設計

- ユーザー種別ごとに主要ユースケースの画面遷移(エントリポイント → 完了)を書く
- 管理者導線は「日常運用で毎日見る画面」と「トラブル時に使う画面」を分けて考える

### 7. 実装指示への落とし込み

- MVP(または次 Phase)について、implementation-planner に渡せる粒度
  (機能・画面・権限・データの概要)まで具体化する

# Output Template

```md
# 仕様整理: <機能名>

## 目的
(誰の・どんな課題を・どう解決するか)

## ユーザー種別
| 種別 | 説明 | この機能での役割 |
|---|---|---|

## 機能一覧
| # | 機能 | 対象ユーザー | Phase | 備考 |
|---|---|---|---|---|

## MVP範囲
- 含む: (理由付き)
- 含まない: (理由付き)

## Phase分け
| Phase | 内容 | リリースで可能になること |
|---|---|---|

## 画面導線
### エンドユーザー
(エントリポイント → 完了までの遷移)
### 管理者
(日常運用 / トラブル対応)

## 権限設計
| 操作 | エンドユーザー | テナント管理者 | 運営 |
|---|---|---|---|

## 運用上の注意
- 監査ログ / export / 通知 / プラン制限 / サポート対応の要件

## 実装指示に落とす内容
(implementation-planner に渡す要約: 機能・画面・権限・データの概要)
```
