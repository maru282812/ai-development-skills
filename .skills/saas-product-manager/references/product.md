## 1. SaaSで漏れがちな機能チェックリスト

ユーザー向け機能を考えた後、必ず以下を確認する。「不要」と判断した場合もその旨を仕様に書き残す。

### 運用・管理

- [ ] 運営側の一覧・検索画面(ユーザー、テナント、対象データを運営が探せるか)
- [ ] 運営によるデータ修正手段(サポート対応で必要になる操作は何か)
- [ ] 無効化・凍結(削除ではなく止める手段。誤操作・不正利用対応)
- [ ] テナント管理者向けのメンバー管理(招待・権限変更・除外)

### ログ・監査

- [ ] 監査ログ(誰が・いつ・何をしたか。権限変更・課金・個人情報操作は必須)
- [ ] 操作履歴のユーザー向け表示の要否

### データ入出力

- [ ] CSV / export(一覧があるなら export 要望はほぼ必ず来る。MVPで作るかは別判断)
- [ ] CSV import の要否(あるなら validation・エラー行の扱いまで仕様化)

### 通知

- [ ] メール通知(何のイベントで・誰に・配信停止はあるか)
- [ ] アプリ内通知の要否

### 課金・プラン

- [ ] この機能はどのプランで使えるか
- [ ] 数量制限(件数・メンバー数・容量)とプランの関係
- [ ] 制限超過時の挙動(ブロックか、警告か、アップセル導線か)

### ライフサイクル

- [ ] データの削除要件(ユーザー退会・テナント解約時にこの機能のデータをどうするか)
- [ ] 空状態(データ0件の初回体験)とオンボーディング

## 2. MVP判断の基準

MVP に**残す**条件(すべて満たすもの):

1. これがないと主要ユースケースが完了しない
2. 後から追加するとデータ構造・権限設計が壊れる(例: テナント分離、権限の階層)
3. リリース初日から運用に必須(例: 運営がユーザーを確認する手段)

MVP から**外してよい**典型:

- export / import(手動対応でしのげる)
- 通知(初期ユーザーには口頭・メール手動で代替可能)
- 高度なフィルタ・ソート・検索(件数が少ないうちは不要)
- 編集履歴・バージョン管理
- プラン別制限(全員同一プランで開始し、課金開始時に追加)

注意: **権限設計とテナント分離だけは後回しにしない**。
UIや通知は後付けできるが、データ構造に染み込む要素は MVP 時点で正しく設計する
(実装は簡易でも、テーブル設計は将来の権限を見据える)。

## 3. 権限・テナント設計の整理方法

### 権限マトリクスの書き方

操作は CRUD + α(承認、招待、export など)まで分解して書く。「管理できる」のような曖昧な行を作らない。

| 操作 | エンドユーザー | テナント管理者 | 運営 |
|---|---|---|---|
| タスク閲覧 | 自分の所属プロジェクトのみ | テナント内すべて | 全テナント |
| タスク作成 | ○ | ○ | ×(代行時は監査ログ必須) |
| メンバー招待 | × | ○ | ○ |
| export | × | ○ | ○ |

### テナント構造の確認事項

- 階層: user → organization(→ project)のどの単位でデータを分離するか
- 1ユーザーが複数テナントに所属できるか(できるなら「現在のテナント」の切り替えUIが必要)
- 運営(自社)はテナント横断でデータを見るか → service_role 利用箇所と監査ログ要件に直結

この整理結果は [db-designer](../../db-designer/SKILL.md) の RLS 設計、
[security-review](../../security-review/SKILL.md) の認可確認の入力になる。
