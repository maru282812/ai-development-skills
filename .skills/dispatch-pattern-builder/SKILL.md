# Purpose

LLM が絡む処理を **Anthropic API 課金を使わずに** 実装するための、決まった構成（指示文ディスパッチ方式）で機能を設計し、実装フェーズに渡せる成果物を出す。

サイト（Next.js + Supabase）は**LLM を一切呼ばない**。やることは「対象を DB に保存し、ID を発行し、コピー可能な**スキル実行文**を表示する」だけ。重い処理（解析・生成・検証）はユーザーがその実行文を **Claude Code / Codex に貼る**ことで、サブスク側のエージェントが実行し、結果を API 経由で書き戻す。

このスキルは2つの成果物を出す:

1. **サイト側の実装指示文＋設計** — 対象保存テーブル / ID発行 / 状態遷移 / API契約(GET・POST) / スキル実行文テンプレ / コピーUI。実コードは書かず [implementation-planner](../implementation-planner/SKILL.md) → Claude Code 実装へ渡す。
2. **機能専用の受け側スキル** — Claude Code に貼られて動く SKILL.md。ID で対象を GET → サブスクで処理 → 結果を POST で書き戻す。参照実装は AI Testmaster の testmaster-test-plan / testmaster-run-api / testmaster-run-screen。

# Why this pattern (前提として必ず守る思想)

この構成が成立する理由を理解していないと、設計がぶれる。核は次の4つ:

- **サイトは LLM を呼ばない。** サイト側にLLM呼び出し・APIキーを置いた瞬間にこの方式の意味（課金回避）が消える。サイトの責務は「保存・ID発行・状態管理・実行文の生成と表示」だけに限定する。
- **スキル実行文は自己完結していること。** ユーザーは実行文をコピーして別のエージェントに貼るだけ。だから実行文には「どの受け側スキルを使うか」「対象ID」「APIベースURL」が含まれ、会話の文脈なしで処理を開始できる必要がある。
- **状態で進捗を表す。** 対象は「未処理 → 処理待ち → 処理済」のような状態を持ち、サイトは件数を表示する（例: 収集 11 / 解析待ち 11 / 解析済 0）。受け側スキルが書き戻すたびに状態が進む。冪等に作る（同じIDを再処理しても壊れない）。
- **外部エージェントが API を叩く前提。** 受け側スキルはサイト外から API を呼ぶ。だから認証（トークン等）と、対象取得 GET・結果書き戻し POST の契約を最初に決める。

# When To Use

- LLM 処理が必要だが、サイト側で API 課金したくない
- 「対象を貯めておいて、あとでまとめて Claude Code で処理して書き戻す」運用にしたい
- studyId のような ID を発行し、コピー用のスキル実行文を画面に出したい
- testmaster と同じ「保存→エージェント処理→書き戻し」型で新機能を作りたい

要件・対象がまだ曖昧（何を保存し何を処理するか未定）なら、先に
[requirements-discovery](../requirements-discovery/SKILL.md) /
[saas-product-manager](../saas-product-manager/SKILL.md) で固める。
このスキルは「構成が決まった機能を、ディスパッチ方式の設計＋受け側スキルに落とす」ことに特化する。

# Procedure

### 1. 機能の核を確定する

推測で設計しない。次の4点をユーザーと確定する（不明なら質問する）:

- **対象(target)**: 何を DB に保存するか。1件の単位は何か（例: 収集したコンテンツ1本、面接1セッション）。
- **重い処理**: Claude Code 側で何をするか（解析 / 生成 / 検証 / 抽出）。入力と出力の形。
- **書き戻す結果**: 処理後に何を保存し、状態をどう進めるか。
- **誰が実行文を使うか**: 運営者だけか、エンドユーザーもか（認証・権限に効く）。

### 2. 状態遷移を決める

対象の状態(status)を列挙し、遷移を一方向で定義する。最低限「未処理 → 処理待ち → 処理済」。
失敗状態（処理エラー）と再実行の扱いも決める。サイトはこの状態ごとの件数を表示する。

### 3. サイト側 API 契約を決める

受け側スキルがサイト外から叩く前提で、最小2本を設計する。詳細は
[references/api-and-auth.md](references/api-and-auth.md) を参照:

- **GET（対象取得）**: ID（または status フィルタ）で未処理の対象を返す。受け側スキルが処理に必要な情報を過不足なく含める。
- **POST（結果書き戻し）**: 処理結果を受け取り、対象の status を進める。冪等性・認証・バリデーションを定義する。

### 4. スキル実行文テンプレを設計する

画面に表示し、コピーボタンで取れる**スキル実行文**を作る。自己完結が条件:

- 使う受け側スキル名（例: `<feature>-run`）
- 対象を取得するためのID（例: `studyId: <uuid>`）と APIベースURL
- 1〜2文で「何をしてほしいか」

例（収集コンテンツの解析）:
```
<feature>-run スキルで次を実行して中身を精査してください（studyId をコピーできます）:
studyId: 0c616b01-14cf-425d-9c17-32cd289f2148
API: https://example.com
```

### 5. コピーUI を設計する

スクショの形（状態バッジ＋件数＋ID＋「スキル実行文をコピー」ボタン＋「進捗を更新」）を踏襲する。
表示項目・状態・空/ローディング/エラーを [feature-spec-writer](../feature-spec-writer/SKILL.md) の画面節の粒度で書く。
実コードは書かない（実装フェーズへ渡す）。

### 6. 受け側スキルを生成する

その機能専用の SKILL.md を1本作る。テンプレと手順は
[references/receiver-skill-template.md](references/receiver-skill-template.md) に従う。
受け側スキルの責務は「ID で GET → サブスクで処理 → POST で書き戻し → 状態を進める」。
自分が実行できる対象だけ処理し、できないものは飛ばす（testmaster-run-* と同じ思想）。

### 7. セルフチェック

- サイト側にLLM呼び出し / APIキーが**混入していないか**（混入＝この方式の破綻）
- スキル実行文だけ読んで（会話文脈なしで）受け側スキルが処理を開始できるか
- GET が返す情報だけで処理が完結するか（追加の隠れ依存がないか）
- POST が冪等か（同じIDを再処理しても二重書き込みにならないか）
- 状態遷移に抜け（処理失敗→再実行の経路）がないか
- サイト側成果物がそのまま implementation-planner に渡せる粒度か

# Output Template (サイト側 実装指示文＋設計)

```md
# ディスパッチ方式 実装設計: <機能名>

## 目的 / 課金回避の狙い
(何の重い処理を、なぜエージェント側に逃がすのか)

## 対象(target)
- 1件の単位:
- 保存する情報:

## 状態遷移
未処理 → 処理待ち → 処理済 (+ 失敗 / 再実行)
| 状態 | 意味 | 次へ進む条件 |
|---|---|---|

## DB
\```sql
-- target テーブル(status 列を含む) migration SQL
\```

## API 契約
### GET <対象取得>
- 入力: id / status フィルタ
- 出力: 受け側スキルが処理に必要な情報一式
- 認証:
### POST <結果書き戻し>
- 入力: 処理結果 + 対象id
- 動作: 結果保存 + status 前進（冪等）
- 認証 / バリデーション:

## スキル実行文テンプレ
(画面に出してコピーさせる自己完結テキスト。受け側スキル名 + ID + APIベースURL を含む)

## コピーUI
- 表示: 状態バッジ / 件数(未処理・処理待ち・処理済) / ID / コピーボタン / 進捗更新
- 状態: 空 / ローディング / エラー

## 受け入れ条件
- [ ] サイトはLLMを呼ばない
- [ ] 実行文コピー→Claude Codeに貼る→処理→書き戻しで状態が進む
- [ ] 同じIDの再処理で壊れない

## 実装フェーズへの引き渡し
implementation-planner → Claude Code。順序: migration → API → コピーUI。
```

受け側スキルの出力テンプレは [references/receiver-skill-template.md](references/receiver-skill-template.md)。
実例の方式メモは [[skill-dispatch-pattern]]（メモリ）。
