# API 契約と認証の決め方

サイト(Next.js + Supabase)は LLM を呼ばない。外部エージェント(Claude Code / Codex)が
叩く前提で、対象取得 GET と結果書き戻し POST を設計する。

## 状態(status)ライフサイクル

対象は一方向の状態を持つ。最小構成:

| status | 意味 | 遷移元 → 遷移先 |
|---|---|---|
| `pending` (未処理) | 保存直後 | → ready |
| `ready` (処理待ち) | 処理対象として確定 | → done / failed |
| `done` (処理済) | 書き戻し完了 | （終端 / 再実行で ready へ戻せる） |
| `failed` (失敗) | 処理エラー | → ready（再実行） |

サイトは status ごとの件数を表示する（例: 収集 11 / 解析待ち 11 / 解析済 0）。
スクショの「進捗を更新」ボタンは件数の再取得。

## GET（対象取得）

受け側スキルが処理に必要な情報を**過不足なく**返すのが要点。隠れ依存を作らない。

```
GET /api/<resource>/{id}
GET /api/<resource>?status=ready        # まとめて取得する場合
```

返却例:
```json
{
  "id": "0c616b01-...",
  "status": "ready",
  "items": [ { "id": "...", "content": "...", "type": "..." } ]
}
```

## POST（結果書き戻し）

```
POST /api/<resource>/{id}/results
```

リクエスト例:
```json
{
  "results": [ { "itemId": "...", "verdict": "pass", "detail": "...", "evidence": "..." } ]
}
```

サーバ側の責務:
- 結果を保存
- 対象/各itemの status を前進
- **冪等**: 同じ itemId の再 POST は upsert（二重作成しない）
- バリデーション（不正な verdict・未知の itemId を弾く）

## 認証

外部エージェントがサイト外から叩くため、公開エンドポイントにしない。選択肢:

- **サービストークン**: 受け側スキルがヘッダ `Authorization: Bearer <token>` を付ける。
  トークンは環境変数 or ユーザー貼り付け。運営者専用運用ならこれが簡単。
- **Supabase RLS + ユーザーJWT**: エンドユーザーも実行文を使う場合。対象の所有者だけが
  GET/POST できるよう RLS を張る。
- 最小権限: GET は対象取得のみ、POST は結果書き戻しのみ。管理操作と分ける。

MVP は「運営者がサービストークンで叩く」で始めるのが軽い。エンドユーザー開放が要件に
入ったら RLS ベースへ。認証方式は要件（誰が実行文を使うか）で決まる。

## よくある落とし穴

- サイト側に LLM 呼び出しを足してしまう → 課金回避が崩れる。サイトは保存と表示だけ。
- GET の情報不足で受け側スキルが追加取得を強いられる → GET を自己完結に。
- POST が非冪等で再実行のたびに重複 → upsert / 処理済みスキップ。
- status の失敗→再実行経路がない → 一度失敗すると詰まる。
