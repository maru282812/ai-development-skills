# Purpose

料金・事業判断・提供範囲・見積り・計画などの「判断物」を、敵対的な複数視点から攻撃し、
前提の甘さ・見落とし・失敗シナリオを**具体的な反例**として提示する。

目的は否定ではない。「反例に耐えた判断」に鍛え上げることと、
崩れる判断を**実行前に**崩しておくこと。自分では気づけない前提の甘さは、
賛成意見をいくら重ねても出てこない——敵対視点を強制することでしか出ない。

原則:

- **read-only**: 対象の文書・判断を勝手に書き換えない。攻撃結果を報告して止まる
- **反例は具体的に**: 「リスクがある」「懸念される」のような抽象的指摘は禁止。
  「誰が・何をしたら・どう壊れるか」のシナリオまで落とす
- **代替案は攻撃の後**: 先に代替案を出すと攻撃が甘くなる。潰し切ってから修正候補を添える

# When To Use

- 料金プラン・プラン構成を公開/提案する前に穴を潰したい
- 事業仮説・新業種展開・重要な意思決定の前提を検証したい
- 提供範囲・見積り・スケジュールが甘くないか疑いたい
- 仕様書・計画書に「都合の良い前提」が混ざっていないか確認したい

対象がコードなら [code-review](../code-review/SKILL.md) / [security-review](../security-review/SKILL.md)、
テスト台帳なら testmaster-adversarial-review、
discovery 成果物群の横断整合性なら [discovery-auditor](../discovery-auditor/SKILL.md) を使う。

# Procedure

### 1. 対象と成立条件を確定する

- 攻撃対象（文書・判断・数字）を特定し、全文を読む
- 「この判断が成功と言えるのは何が真のときか」を1〜3文で言語化する
- 判断が暗黙に依存している**前提を列挙する**（例: 「顧客は月額に抵抗がない」
  「解約率は低い」「競合は同価格帯に来ない」「運用は月5時間で回る」）。
  前提の列挙が攻撃の土台になる——ここが浅いと攻撃も浅くなる

### 2. 敵対視点を選ぶ（3〜5視点）

対象に効く視点を選び、選定理由を1行ずつ添える:

| 視点 | 何を突くか |
|---|---|
| 顧客・契約先 | 「この金額・条件で本当に払うか」「他社と比べてどう見えるか」「解約の引き金」 |
| 競合 | 「同じものをより安く/速く出されたら」「差別化は模倣可能か」 |
| 悪意ユーザー | 「規約・料金・仕組みの悪用方法」「タダ乗り・転売・規約すり抜けの経路」 |
| 会計・投資家 | 「数字の根拠」「単価×件数の現実性」「隠れコスト」「最悪ケースの資金繰り」 |
| 法務・規制 | 「表記・約束が法的義務を生まないか」「返金・解約条件の穴」 |
| 運用現場 | 「誰がその作業を毎日やるのか」「問い合わせが増えたら回るか」「属人化」 |
| 半年後の自分 | 「この判断で縛られる将来の選択肢」「やめたくなった時に撤退できるか」 |

### 3. 攻撃する（視点 × 前提）

- 各視点から、手順1で列挙した前提に反例をぶつける
- 1つの反例＝1つの具体シナリオ:「誰が・どんな状況で・何をしたら・何が壊れるか」
- 数字がある対象（料金・見積り）は数字自体を疑う: 根拠は? 半分だったら? 2倍かかったら?
- 「攻撃できなかった前提」も明記する——耐えた前提は判断の強い部分として残す

### 4. 重大度で分類する

- **Critical**: この前提が崩れると判断全体が成立しない（実行前に解消必須）
- **Major**: 特定条件下で崩れる。対策か撤退条件の事前定義が要る
- **Minor**: 判断は成立するが改善余地がある

### 5. 差し戻しレポートを出して止まる

Output Template で報告し、**対象は修正せずに停止する**。
Critical / Major それぞれに修正候補を1〜2案添えるが、採否はユーザーが決める。
修正後の再攻撃（2周目）を提案してよい。

# Output Template

```md
# 敵対的レビュー: <対象>

## 対象と成立条件
(何が真ならこの判断は成功か)

## 依存している前提
| # | 前提 | 攻撃結果 |
|---|---|---|
| P1 | ... | 崩れた(→C1) / 耐えた |

## 攻撃結果
### Critical
- **C1. <タイトル>** [視点: 顧客]
  - シナリオ: 誰が・何をしたら・どう壊れるか
  - 崩れる前提: P1
  - 修正候補: ...
### Major / Minor
(同形式)

## 耐えた前提（この判断の強い部分）
- ...

## 次のアクション
- [ ] Critical を解消 → 再攻撃(2周目)を実行
```

# Dispatch 対応（受け側モード）

対象が[[dispatch-pattern-builder]]方式のスキル実行文（ID + API ベースURL）で渡された場合:

1. `GET /api/<resource>/{id}` で攻撃対象（判断物のテキスト・数字）を取得する
2. 上の Procedure で攻撃する（read-only 原則は同じ）
3. 結果（重大度別の指摘リスト）を `POST /api/<resource>/{id}/<writeback>` で構造化して書き戻し、
   status を進める。冪等に（同じIDの再攻撃は前回結果を上書き）

実行文がない通常の依頼では、このセクションは無視してよい。

# 実行モデルティア

推奨ティア: **deep**（反例の発見力・攻撃の網羅性がモデルの推論力に直結する）。
最上位推論クラスのモデルが使えない環境でも中止しない。代わりに劣化運転として、
視点を3つに絞って1視点ずつ区切って提示し、確信度の低い攻撃には「要検証」を付け、
攻撃の網羅性を断定しない（「上位モデルでの再攻撃を推奨」と明記する）こと。
具体的なモデル名はここに書かない（対応表は `.skills/MODEL-TIERS.md`）。
