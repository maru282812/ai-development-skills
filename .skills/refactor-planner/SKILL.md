# Purpose

既存機能の挙動を一切変えずに、コードの構造(責務・重複・分割)を改善する計画を作成する。

必ず扱う項目:

- 現状の責務(各ファイル・関数が何をしているか)
- 重複(同じロジックが何箇所にあるか)
- 共通化候補(まとめるべきもの・まとめるべきでないもの)
- 分割候補(大きすぎるファイル・コンポーネント)
- レイヤ分離(service / repository / controller(route) / component)
- 影響範囲(変更が波及する利用元)
- 段階的移行(一度に全部変えない手順)
- regression 確認(壊れていないことの確認方法)

# When To Use

- ファイル・コンポーネントが大きくなりすぎて手を入れにくい
- 同じ処理のコピペが増えてきたので共通化したい
- データアクセスとUIが混ざっているので層を分けたい
- 機能追加の前に、土台を整理しておきたい

リファクタと同時に機能を変えたい場合は、**先にこのスキルで整理 → 後で
[implementation-planner](../implementation-planner/SKILL.md) で機能追加**の2段に分ける。
挙動変更とリファクタを同じ変更に混ぜない。

# Procedure

### 1. 動機と範囲の確認

- 何に困っているか(変更しづらい・読めない・重複)と、対象範囲を確認する
- 「挙動は変えない」を原則として確認する。例外(バグを直したい等)があれば別タスクに分離する

### 2. 現状分析

- 対象ファイルの責務を列挙する(1ファイルに何種類の仕事があるか)
- 重複を検索で特定する(類似の Supabase クエリ、同じ整形処理、コピペされた UI ブロック)
- 利用元を洗い出す(調査は [system-investigator](../system-investigator/SKILL.md) の手順)

### 3. あるべき構造の設計

- レイヤ分離・分割の方針は [references/refactoring.md](references/refactoring.md) セクション1〜2に従う
- 過剰な抽象化を避ける: 2回しか出ない重複は無理にまとめない、レイヤはプロジェクト規模に合わせる
- 既存のプロジェクト規約(ディレクトリ構成・命名)に合わせる

### 4. 段階的移行手順の設計

- 1ステップ = 「ビルドが通り、既存テスト・動作確認が通る」単位に分割する
- 移行の定石(新設→付け替え→削除)は [references/refactoring.md](references/refactoring.md) セクション3を参照
- 各ステップの後に regression 確認を挟む

### 5. regression 確認方法の定義

- 既存の自動テストの有無を確認し、なければ「リファクタ前に最低限の特性テスト(現状の挙動の固定)を書く」ことを検討する
- 手動確認項目は対象機能の主要導線に絞って列挙する(詳細化は [test-planner](../test-planner/SKILL.md))

### 6. 計画の出力

- ステップごとに、AIエージェントに渡せる粒度の指示にまとめる
- 「やらないこと(挙動変更・スコープ外のついで修正)」を明記する

# Output Template

```md
# リファクタ計画: <対象>

## リファクタ目的
(何に困っていて、終わったら何が良くなるか)

## 現状の問題
| # | 箇所 | 問題(責務過多/重複/密結合) |
|---|---|---|

## 分割方針
(あるべき構造。レイヤ・ディレクトリ・命名)

## 共通化候補
| 対象 | 現在の箇所 | 共通化先 | 備考 |
|---|---|---|---|

## 変更ファイル
| 種別(新規/修正/削除) | パス | 内容 |
|---|---|---|

## 影響範囲
- (利用元と、波及しうる既存機能)

## 段階的実施手順
### Step 1: <名前>
- 内容 / 完了条件(ビルド・確認が通ること)
### Step 2: ...

## 回帰確認
- [ ] (各ステップ後に確認する項目。既存テスト・主要導線)
```

実例は [examples/](examples/README.md) を参照。
