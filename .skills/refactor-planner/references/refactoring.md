## 1. Next.js + Supabase のレイヤ分離

中規模プロジェクトでの現実的な分離(フルDDDにしない):

```text
app/**/page.tsx          # 表示の組み立てのみ。データ取得は呼ぶだけ
app/**/route.ts          # HTTP の入出力(parse, 認証, ステータスコード)のみ
app/actions/*.ts         # Server Actions。認証・validation・サービス呼び出し
components/**            # UI。データ取得ロジックを持たない(propsで受ける)
lib/services/*.ts        # 業務ロジック(複数テーブルにまたがる処理、判断)
lib/repositories/*.ts    # Supabase アクセス(.from() をここに集約)— 規模が小さければ services と統合可
lib/validations/*.ts     # zod スキーマ(UI と API で共有)
lib/utils/*.ts           # 純粋関数(日付・金額整形など)
```

レイヤ分離の判断:

- **repository 層を分ける価値があるのは**: 同じテーブルへのクエリが3箇所以上に散っている、
  select するカラムやJOINがバラバラで型が不安定、テスト時にDBアクセスを差し替えたい場合
- **service 層を分ける価値があるのは**: 1つの操作が複数テーブル・外部APIにまたがる、
  同じ業務ルール(権限判定、状態遷移)が複数のAPIから呼ばれる場合
- ページが1つしかない小機能に4層を強制しない。「散らばった .from() の集約」だけでも価値は大きい

よくある責務違反のシグナル:

- `'use client'` コンポーネント内に Supabase クエリ・業務判断が直書き
- `page.tsx` が 300 行超で、データ取得・整形・表示がすべて入っている
- 同じ `.from('xxx').select(...)` が微妙に違う形で5箇所にある
- route.ts に業務ロジックがあり、同じ処理が Server Action 側にもコピーされている

## 2. 分割・共通化の判断基準

### 共通化してよいもの

- **同一の業務ルール**(権限判定、状態遷移、料金計算): 仕様が1つなので実装も1つにする
- 同一テーブルへのクエリ(repository に集約)
- バリデーションスキーマ(UIとAPIで共有)
- 完全に同形のUIパターン(確認ダイアログ、トースト)

### 共通化を急がないもの

- **「たまたま今同じ」コード**: 見た目が似ていても変更理由が違うものをまとめると、
  条件分岐だらけの共通関数になる(間違った抽象化)。重複2回までは静観してよい
- props が増え続けている共通コンポーネント(`variant` が4つを超えたら分割のサイン)

### 分割の基準

- コンポーネント: 「状態を持つ容れ物」と「表示するだけの部品」に分ける。
  1ファイルで `useState` が5個以上 / JSX が200行超なら分割候補
- 関数: 「〜して〜して〜する」と説明される関数は分割候補
- ファイル: 異なる理由で変更される複数の関数が同居していたら分割(変更理由ごとに1ファイル)

## 3. 挙動を壊さない移行の定石

### 基本形: 新設 → 付け替え → 削除

```text
Step 1: 新しい関数・ファイルを追加する(既存コードは触らない)
        → ビルド・既存動作に影響なし
Step 2: 利用元を1箇所ずつ新実装に付け替える
        → 1箇所ごとに動作確認。問題があれば戻すのも1箇所分
Step 3: 全利用元の移行後、旧実装を削除する
        → 削除時に grep で参照ゼロを確認
```

### ルール

- **rename と移動とロジック変更を同じコミットでやらない**。移動だけのコミットは diff が読めるが、混ぜると検証不能になる
- 1ステップ = 「`npx tsc --noEmit` と `npm run build` が通り、対象機能の主要導線が動く」単位
- export の互換を保つ: 旧ファイルから `export { x } from './new-location'` で再エクスポートしておけば、利用元の付け替えを後回しにできる
- リファクタ中に見つけたバグは**直さずに記録する**(直すなら別コミット・別タスク)。「壊さない」検証ができなくなるため

### regression 確認の最低ライン

- 自動テストがあれば各 Step 後に実行
- なければ: リファクタ前に対象機能の現状挙動をメモし(スクリーンショット・レスポンスの控え)、各 Step 後に同じ操作で比較する
- 仕上げに [code-review](../../code-review/skill.md) の観点(特に「既存機能への影響」)で最終確認する
