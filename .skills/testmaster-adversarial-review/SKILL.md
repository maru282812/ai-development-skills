# testmaster-adversarial-review（テスト台帳の対抗レビュアー）

testmaster は「全テスト項目を挙げて、現行バージョンに対する合格％を見る」設計。
[[testmaster-test-plan]] が**分母（項目）を作り**、[[testmaster-run-api]] / [[testmaster-run-screen]] が**合否を埋める**。
このスキルはその両方の成果物を **疑う担当** ——「この台帳とこの％は、本当に正しさを保証しているのか？」を攻撃者目線で突く。

生成側が optimistic（網羅したつもり）になりがちな所を、対抗側として pessimistic に検算するのが価値。
自分でテストを作り直したり実行したりはしない。**判定し、差し戻し指示を出して止まる**（[[agent-tester]] と同じ停止ゲートの思想）。

```text
1. 台帳を取得（GET）— suggestions（項目）と runs（合否履歴）と project.context（成功条件）
2. 各項目の現行状態を自分で再計算（passed/failed/blocked/stale/untested）
3. 対象アプリの実コードを読み、台帳と突き合わせる
4. 3つの軸で批判:
   A. 抜けている観点（coverage gaps）
   B. 甘い受け入れ条件（落ちようがない項目）
   C. 偽の合格（証拠なし合格 / stale を見落とした「カバー済み」錯覚）
5. 重大度を付けて「対抗レビュー・レポート」を出す
6. 差し戻し指示（再生成 or 項目強化の具体文）を添えて止まる
```

## 入力（足りなければ一度にまとめて確認）

- **projectId** — testmaster のプロジェクト ID（`C:\work` 配下フォルダ名の slug。例 `ai-chat-interview`）。
- **対象アプリのコードパス** — 台帳が対象にしているリポジトリのルート。
- **testmaster のベース URL** — 既定 `http://localhost:3400`。

## 手順

### 1. 台帳を取得して状態を再計算

`GET {baseUrl}/api/projects/{projectId}` を叩き、`bundle` から以下を読む:

- `bundle.suggestions[]` — テスト項目（分母）。各 `{ id, area, category, title, description, priority, level, sourceFingerprint }`。
- `bundle.runs[]` — 合否履歴。各 `{ suggestionId, result, notes, sourceFingerprint, createdAt }`。`result` は `passed | failed | blocked | not-run`。
- `bundle.project.context` — `{ users, constraints, successCriteria }`。コードに書いていない「何が重要か」。受け入れの甘さを判定する基準にする。
- `bundle.surfaces[]` — サーフェス台帳（設計網羅率の横軸）。各 `{ key, kind, name, area, applicablePerspectives, na[] }`。
- レスポンス直下の `designCoverage` — `{ percent, total, covered, na, gap, gaps[], naCells[] }`。
  **設計網羅率（分母の十分性）**。`gaps[]` は項目ゼロの空セル（`surfaceName × perspective`）、`naCells[]` は理由付き対象外。
  これは §3-D の一次情報。無い（surfaces 未登録）なら「フル網羅台帳が無い＝設計網羅率が測れない」ことを指摘に含める。

**各 suggestion の現行状態を自分で計算する**（testmaster の完了判定と同じ規則。偽の合格を見抜く核なので必ず手元で再現する）:

- その項目の run を `createdAt` 降順に並べ、`run.sourceFingerprint === suggestion.sourceFingerprint` の run（=現行バージョンの検証）だけを「現行 run」とする。
- 現行 run の最新が `passed` → **passed**（これだけが完了の分子）。`failed`/`blocked` → そのまま。
- 現行 run が無く、過去に（旧 fingerprint で）`passed` があった → **stale**（改修で合格が無効化された。要再テスト）。
- それ以外 → **untested**。

`percent = passed / total`。critical+high を別集計（= important）。**stale と untested を分けて持つ**——「昔は通っていた」を「今カバー済み」と勘違いさせないため。

### 2. 対象コードと突き合わせる

ルーティング定義・API ハンドラ・主要画面/機能を Grep/Glob/Read で洗い出す（[[testmaster-test-plan]] と同じ一次情報＝実コード）。
**実在する** endpoint / feature を確定し、台帳の `area` と対応づける。コードにあるのに台帳に area が無いものは丸ごと抜け。

### 3. 三軸で批判する

#### A. 抜けている観点（coverage gaps）

各 area（endpoint / 機能）に、下の観点が**そろっているか**を機械的に当てて、欠けを挙げる。
「項目が存在するか」ではなく「**この観点の不合格を捕まえられる項目があるか**」で見る。

- 正常系（主要ユースケースの完了）
- 入力検証（必須欠落・型不正・長さ/形式）
- 認証・認可（無トークン→401、権限外・他テナント→403、IDOR）
- 異常系（404 / 409 / 5xx を出さない、失敗が中途半端に残らない）
- 境界・空・ページング上限
- 領域固有リスク（コードの分岐・状態遷移・副作用から読み取れるもの）

`project.context.successCriteria` があるのに、それを直接検証する受け入れ項目が `Project-wide` に無ければ**重大な抜け**として挙げる（「機能は通るがプロダクトの成功条件は誰も検証していない」状態）。

#### B. 甘い受け入れ条件（落ちようがない項目）

合格しても正しさを保証しない項目を暴く。**「どう壊れていてもこの項目は通ってしまうか？」**と自問する。落ちようがない項目は、合格＝無意味。典型:

- title/description が「動作すること」「表示されること」止まりで、**入力→期待 status/挙動が具体でない**。
- 期待結果が反証可能でない（「正しく動く」ではなく「limit=10000 で 400 と明示エラー、500 を出さない」のように falsifiable か）。
- 1項目に複数の判定を詰め込み、どれが落ちたか分からない。
- `level: rough` のまま critical/high に居座り、detailed に割られていない（粗いまま重要扱い）。

**強い/弱いの対比:**
- 弱い: 「ユーザー一覧が表示される」→ 空でも 500 でも“表示”の解釈次第で通る。
- 強い: 「GET /users 認証あり・0件で 200 と空配列、`items:[]` を返す（null や 500 でない）」。

#### C. 偽の合格（false pass）

`passed` を額面どおり信じない。次を `passed` 項目に対して当てる:

- **stale なのに人の頭では「カバー済み」**: §1 で stale 判定された項目。％の分子には入らないが、レポートや記憶で「通ってる」と誤認されがち。改修で失った合格として明示する。
- **証拠なし合格**: 現行 run はあるが `notes` が空 or「OK」だけで、**何を送って何を確認したか**が無い。再現も反証もできない合格は疑う。
- **甘い項目の上の合格**: §B で弱いと判定した項目の合格は、二重に無価値。
- **critical/high が単発の浅い合格に依存**: 重要項目ほど証拠の濃さを要求する。

#### D. 空セルと怪しい N/A（設計網羅率の穴）

`designCoverage` を使い、**分母マトリクスそのものの穴**を突く。実施率(passed%)が高くても、
そもそも項目を作るべきセルが空なら「網羅したつもり」の錯覚。§A が観点の抜けを人手で探すのに対し、
ここは **サーバが機械計算した gap/na** を根拠に、より確度高く突く。

- **空セル（gaps）**: `designCoverage.gaps[]` の各 `surfaceName × perspective` は **項目ゼロ**。
  重要サーフェス（認証必須 endpoint の `authn/authz/rls`、課金・破壊系の `error/domain-specific`）の gap を最優先で挙げる。
- **怪しい N/A（naCells）**: `na` は「理由付きで対象外」。理由が **実コードと矛盾**していないか検算する:
  - 「公開APIなので authz は na」と書いてあるのに、コードは認証を要求している → **偽の na**（本当は gap）。
  - 「MVP対象外」等の先送り理由が critical サーフェスに付いている → 妥当か確認事項に上げる。
- **surfaces 自体の欠落**: `bundle.surfaces` に実在するサーフェスが載っていない（inventory 漏れ）なら、
  そのサーフェスは設計網羅率の分母にすら入っていない＝二重の抜け。実コードと突き合わせて指摘する。

#### 認可・所有者まわりの指摘は「二段階」で検証する（過剰断定を避ける）

「他人のデータに到達できる（IDOR）」系の指摘は、**アプリ層のコードだけ見て『危険』と採点してはいけない**。
所有者制御は別の層にあることが多く、片方しか見ずに断定すると誤報になる（実例: アプリ層に所有者照合が無くても、それは設計上の前提かもしれない）。必ず次の順で詰める:

1. **enforcement 層を確認してから severity を付ける** — アプリ層に所有者チェックが無いとき、DB 層を見る。
   - Supabase 接続が **service_role キー**なら **RLS は全バイパス**＝DB 層の制御は無い。アプリ層が唯一の砦。
   - **anon/ユーザースコープのクライアント＋RLS** なら、DB 行レベルで所有者が縛られている可能性。アプリ層に無くても実害ゼロのことがある。
   - どちらか確認できるまで「危険」と書かない。「未確認」と明記して差し戻す。

2. **確認後も「exploit 確定」ではなく「仕様 vs 実装のズレ／未決の設計判断」として返す** — どの層にも所有者照合が無いと確認できても、それが直ちにバグとは限らない:
   - **ケイパビリティ・トークン型**（推測不能な UUID を「持っている＝正当」とみなす設計）を**意図的に許容**している場合がある。ID が列挙不能・本人にしか配られない・機微度が低いなら、実運用で許容されるパターン。
   - この場合の正しい指摘は「実装が脆弱」ではなく「**`constraints`/`successCriteria` の文言（"別ユーザーは安全に拒否される"等）が実装より強い。capability 前提なら文言を実態に合わせ、台帳に accepted risk として記録すべき**」。許容しないなら実装が文言に足りていない。
   - どちらを採るかは**ユーザーの設計判断**。対抗レビュアーは決め打ちせず、判断材料（どの層にも照合が無い事実／ID の推測可能性・漏洩経路）を添えて §5 の確認事項に上げる。

### 4. 重大度を付けて報告

各指摘を **重大（リリース判断を誤らせる）/ 高 / 中 / 低** に分類。
特に「important（critical+high）の％を実態より高く見せている要因」を最優先で挙げる——この台帳の存在意義は重要項目の合格％なので、そこを汚す偽合格・抜けが最も害が大きい。

### 5. 差し戻し指示を出して止まる

自分で台帳を書き換えない（理由は §やらないこと）。代わりに、そのまま次工程に渡せる指示を出す:

- **抜け（A）** → 領域単位の追加なら [[testmaster-test-plan]] へ `mode="replace-areas"` で（対象 area と足す観点を箇条書き、他領域を潰さない）。アプリ全体の網羅漏れなら [[testmaster-full-plan]] へ再走査を指示。
- **甘い項目（B）** → 強化後の title/description ドラフトを項目ごとに提示（弱い現状 → 強い改稿の対で）。
- **偽合格（C）** → 再テストが要る項目一覧（stale / 証拠なし）と、run 記録時に残すべき確認内容。
- **空セル・怪しい N/A（D）** → 埋めるべき gap セル（surface × perspective）の一覧と、na 理由を実態に直す指示。サーフェス自体の欠落は [[testmaster-full-plan]] の再 inventory へ。

最後に確認チェックリストを添えてユーザーに返す（勝手に再生成・再実行へ進まない）。

## レポート様式

```md
# 対抗レビュー: <projectId>

## 総合判定
**信頼できる / 注意（％が実態より高い）/ 危険（重要項目が偽カバー）** — 1行要約

## 重要項目（critical+high）の偽カバー要因
| # | area / 項目 | 種別(抜け/甘い/偽合格) | なぜ合格が無意味か | 重大度 |
|---|---|---|---|---|

## A. 抜けている観点
| area | 欠けている観点 | 想定される見逃しバグ |
|---|---|---|

## B. 甘い受け入れ条件
| 項目 | 現状(弱い) | 改稿(反証可能に) |
|---|---|---|

## C. 偽の合格
| 項目 | 状態(stale/証拠なし) | 根拠 | 要対応 |
|---|---|---|---|

## D. 空セルと怪しい N/A（設計網羅率）
設計網羅率 <percent>%（covered <c> / na <n> / gap <g> / 全 <t>）
| surface × perspective | 種別(gap/偽na/surface欠落) | 根拠(実コード) | 重大度 |
|---|---|---|---|

## 差し戻し指示
### 分母の追加（領域単位=test-plan replace-areas / 全体網羅漏れ=full-plan）
- (area とふやす観点 / 埋める gap セル)
### 項目強化ドラフト
- (強い title/description)
### 再テストが必要な項目
- (stale / 証拠なし の一覧)

## 確認事項
- [ ] (ユーザーが Yes/No で返せる確認)
```

## やらないこと（境界）

- **台帳を書き換えない** — `POST .../suggestions/import` も `POST .../runs` も叩かない。GET のみ。生成は [[testmaster-test-plan]]、合否記録は run スキルの仕事で、対抗側が分母や合否を勝手に動かすと検算者と被検算者が同一人物になり、レビューの意味が消える。
- **テスト項目を新規生成して台帳を埋めない** — 抜けは「差し戻し指示」として返すだけ。import は全置換なので部分追記は事故になる。
- **テストを実行しない** — 合否は run スキルが付ける。ここは「その合否は信用できるか」を判定する側。
- **対象アプリのコードを変更しない**（読むだけ）。
- 推測で endpoint/feature を増やして「抜け」を捏造しない。**実在するコード**を根拠にする。
