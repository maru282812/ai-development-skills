# Purpose

実装した(またはこれから実装する)機能に対し、テスト観点を網羅的に洗い出し、
手動確認手順・自動テスト候補・受け入れ条件としてまとめる。

必ず扱う観点:

- 正常系(主要ユースケースが完了するか)
- 異常系(不正入力、失敗時の挙動、エラー表示)
- 権限別(ユーザー種別・ロールごとの可否)
- RLS別(他人・他テナント・未認証での到達不能性)
- UI操作(フォーム、二重送信、画面状態)
- API(request/response、ステータスコード)
- DB(データの整合性、制約、トリガーの副作用)
- regression(既存機能が壊れていないか)
- 手動確認手順(誰でも再現できる手順)
- 自動テスト候補(unit / integration / E2E の振り分け)

# When To Use

- 実装完了後、何を確認すべきか洗い出したい
- リリース前のQAチェックリスト・受け入れ条件を作りたい
- E2E・自動テストのケースを設計したい
- 改修による既存機能への回帰確認項目を作りたい

確認の結果コードの問題を指摘したい場合は [code-review](../code-review/skill.md)、
セキュリティ到達性の確認は [security-review](../security-review/skill.md) と組み合わせる。

# Procedure

### 1. 対象機能と仕様の把握

- 機能の目的・主要ユースケース・対象ユーザー種別を確認する
- 実装計画(implementation-planner の出力)や仕様があればそれを正とし、なければコードから仕様を読み取って「テストの前提」として明示する

### 2. 正常系の列挙

- ユーザー種別ごとに、主要ユースケースの開始→完了を確認項目化する
- 入力のバリエーション(最小・最大・任意項目省略)を含める

### 3. 異常系の列挙

- [references/testing.md](references/testing.md) セクション1の異常系カタログ(不正入力、境界値、失敗時挙動、二重操作、同時操作)から該当するものを選ぶ
- 「失敗したことがユーザーに伝わるか」「データが中途半端に残らないか」を確認項目に含める

### 4. 権限・RLS 観点の列挙

- 権限マトリクス(ユーザー種別 × 操作)を作り、**「できること」と「できないこと」の両方**を確認項目にする
- RLS は UI 経由ではなく Supabase クライアント直(または curl)で他人・未認証アクセスを試す項目を入れる
  (手順は [references/testing.md](references/testing.md) セクション2)

### 5. DB・API 観点の列挙

- API: バリデーションエラー時のステータス・形式、認証なしでのアクセス
- DB: 制約(unique / check / FK)が効いているか、updated_at・トリガー副作用、論理削除の反映

### 6. 回帰確認の列挙

- 変更したテーブル・共通コンポーネント・共通関数の利用元を洗い出し、影響を受けうる既存機能の確認項目を作る
  (調査は [system-investigator](../system-investigator/skill.md) の手順)

### 7. 手動 / 自動の振り分けと完了条件

- 各項目を「手動確認 / unit / integration / E2E」に振り分ける(基準は [references/testing.md](references/testing.md) セクション3)
- 受け入れ条件(これが全部○ならリリース可)を確定する

# Output Template

```md
# テスト計画: <機能名>

## テスト目的
(何を保証するためのテストか。前提とした仕様)

## 正常系
| # | 確認内容 | 手順 | 期待結果 | 種別(手動/自動) |
|---|---|---|---|---|

## 異常系
| # | 確認内容 | 手順 | 期待結果 | 種別 |
|---|---|---|---|---|

## 権限別確認
| 操作 | ユーザー種別A | 種別B | 未認証 |
|---|---|---|---|
(○=可能を確認 / ×=不可能を確認)

## UI確認
- フォーム / 二重送信 / ローディング / 空状態 / エラー表示 / スマホ幅

## API確認
- 認証なしアクセス / バリデーション / ステータスコード

## DB確認
- 制約 / RLS直接アクセス / トリガー副作用 / データ整合性

## 回帰確認
- (影響を受けうる既存機能と確認項目)

## 完了条件
- [ ] (これが全部○ならリリース可、の形で)
```

実例は [examples/](examples/README.md) を参照。
