## 1. 異常系カタログ

機能に応じて該当するものを確認項目化する。

### 入力値

- 必須項目の未入力 / 空文字 / 空白のみ
- 最大長ちょうど / 超過(DB制約と画面バリデーションの一致)
- 数値: 0 / 負数 / 小数 / 上限超え
- 日付: 過去日 / 形式不正 / タイムゾーン跨ぎ
- 選択値: 画面にない値を直接送信(API直叩き)
- 絵文字・サロゲートペア・HTMLタグ入り文字列(XSS確認を兼ねる)
- ファイル: サイズ超過 / 想定外の拡張子・MIME / 0バイト

### 失敗時の挙動

- 通信エラー・タイムアウト時にユーザーへエラーが表示されるか
- 失敗時にデータが中途半端に残らないか(複数テーブル更新の途中失敗)
- エラー後にリトライして正常完了できるか

### 操作の重複・競合

- 送信ボタン連打(二重登録されないか)
- 同一データを2画面で開いて両方から更新(後勝ち?エラー?)
- 削除済みデータへの操作(別タブで削除→元タブで編集保存)
- 戻るボタン・リロード後の再送信

### 状態・ライフサイクル

- データ0件(空状態)の表示
- ページネーション境界(0件、1ページちょうど、最終ページ)
- セッション切れ状態での操作(ログイン画面へ誘導されるか)
- 退会・無効化済みユーザーのデータの表示

## 2. 権限・RLS の確認方法

### 権限マトリクスの確認原則

- 「できる」確認だけでなく、**「できない」ことの確認**を必ず項目化する(認可テストの本体はこちら)
- UI で隠れていても API・DB 直で試す(ボタン非表示は認可ではない)

### RLS の直接確認

UIを経由せず、anon キーのクライアントで直接アクセスして確認する:

```ts
// ユーザーAでログインした状態のクライアントで、ユーザーBのデータに触れないこと
const { data } = await supabase.from('tasks').select('*'); // 他人の行が混ざらないか
await supabase.from('tasks').update({ title: 'x' }).eq('id', '<他人のid>'); // 0件更新になるか
await supabase.from('tasks').insert({ project_id: '<他人のproject>', ... }); // 拒否されるか
```

または SQL で擬似的に確認(ローカル):

```sql
-- 対象テーブルのポリシー一覧
select * from pg_policies where tablename = 'tasks';
```

確認パターン: **未認証(anon)/ 認証済み本人 / 認証済み他人 / 他テナント管理者** の4視点 × select/insert/update/delete。

### API の認証・認可確認

```bash
# 認証なしで 401 が返るか
curl -i https://localhost:3000/api/tasks
# 他人のリソースIDで 403/404 が返るか(Cookieはユーザーaのもの)
curl -i -b "$COOKIE_A" https://localhost:3000/api/tasks/<user_b_task_id>
```

## 3. 手動 / 自動テストの振り分け基準

| 種別 | 向いているもの | 例 |
|---|---|---|
| unit | 入出力が純粋なロジック、バリデーション | zodスキーマ、金額計算、日付処理 |
| integration | DB・RLSを含むデータアクセス層 | Server Action をローカルSupabaseに対して実行 |
| E2E (Playwright等) | クリティカルパスの正常系のみ | サインアップ→主要機能1周、決済 |
| 手動 | 視覚確認、初回のみの確認、コスト>価値のもの | UI崩れ、スマホ表示、文言、空状態 |

振り分けの指針:

- E2E は「壊れたら事業に響く導線」に絞る(多くしすぎると保守不能)
- RLS・認可の確認は integration(または手動のDB直確認)で必ず1回は実施し、重要テーブルは自動化を推奨
- 異常系の大半は unit(バリデーション)+ 手動1回で十分なことが多い
- 回帰確認は「自動テストがある範囲」と「手動で見る範囲」を明示的に分けて記載する
