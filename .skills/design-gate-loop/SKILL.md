# design-gate-loop（見た目の製造工程とゲート）

## Purpose

見た目を持つ成果物が「パワポっぽい」「AIで綺麗に並べただけ」になる原因は4つ（2026-10-21 診断）。

1. 基準が形容詞だけ（余白・字間・行長・写真が数値で無い）→ AI は既定値（中央揃え＋同形角丸カード＋グラデ帯）に落ちる
2. 作ったものをレンダリングして見ていない（見てから直す工程が無い）
3. 写真・図版・余白の役割が未定義で、全部を文字＋枠で置く
4. 1案だけ作って見せ、気に入らなければ作り直す往復

このスキルは**工程**でこの4つを潰す。見た目そのものの判断（配色・タイポ・構造）は hallmark に任せ、
ここでは「どの順で、何を作り、何点で通すか」だけを持つ。

実例: YOTTO 自社LP（website-sales-ai `sites/yotto-lp-a` → https://hp.yottollc.com/ ）。
参照7本実測 → Design System → 候補10本→7本→3本→1本（3周）→ 実装 → ゲート 7/8 → 訴求作り直し → 公開。
経緯は yotto-ops `orders/website-sales-ai/o-2026-10-21-lp-rebuild.md` / `o-2026-10-22-lp-implement.md`、
基準の写しは website-sales-ai `docs/design-system.md`。

## 絶対ルール

1. **基準を数値で持ってから書く。** 参照を実測し、**N本中N本に共通する値だけ**を型にする（1本にしかない値は捨てる）。
   色・角丸はブランドとして自分で決め、参照から借りない（借りると参照のクローンになる）。
2. **候補は「配置違い」でなく「雰囲気違い」。** 同じ型の色違い・配置違いは**1案と数える**。
   3方向を出したつもりが配置違いだった、は差し戻し確定（2026-10-22 実例）。
3. **作ったものは必ずレンダリングして見る。** Playwright で PC/スマホを撮影し、見てから採点・修正する。
   見ていないものを人に出さない。
4. **落とす。** 人に見せるのは自己採点で生き残った候補だけ、**比較ページ1枚**で。全部並べて選ばせない。
5. **見た目OKで終わらない。** 訴求レビュー（§Phase 4）を別工程で通す。見た目が良くなっても
   「TOP で何を売っているか分からない」は起きる（2026-10-25 実例）。
6. **ゲート不合格のまま公開・PR しない。** 採点表（8項目＋パッと見）を PR 本文に貼る。6点未満は直して再採点。
7. **候補に入れる「中の実物」が印象の上限を縛る。** 端末画面やサンプルを候補に入れるなら、
   その実物を先に同じ基準で作り直す（「ちゃんとしている」止まりの実物は候補全体を平凡にする）。

## When To Use

- LP・HP・サービス紹介・資料テンプレ・管理画面など、**人に見せる見た目**を新規に作る／全面に作り直す
- 「パワポっぽい」「AIっぽい」と言われた成果物を基準から立て直す
- 公開・PR 前に、見た目を持つ成果物が人に見せられる水準かを判定したい

使わない場面:

- 単一コンポーネント・一画面の表現を 3〜5 案見比べたい → [[design-variant-preview]]
- 参照サイトを探すところから方向性を決めたい → [[design-reference-scout]]（本スキル §Phase 0 の前段）
- 見た目は決まっていて、文言・導線の使い勝手を診たい → [[ui-ux-review]]
- 動作の検証（表示・操作・console）→ [[verification-loop]]（本スキルのゲートは見た目の合否、動作はそちら）

## Procedure

```
Phase 0 基準      参照実測 → 共通項だけ型に → Design System（tokens＋ゲート）
Phase 1 候補      実HTML 7〜10本 → 撮影 → 採点 → 落とす → 比較ページ → 人が絞る → 2〜3周 → 1本
Phase 2 実装      hallmark を読んで本命を実装。他候補の良い要素は「取り込みリスト」で足す
Phase 3 ゲート    8項目採点＋パッと見採点＋旧版/候補との比較スクショ → PR 本文へ
Phase 4 訴求      3問で判定し、面の順序を「読み手の判断順」に組み直す（見た目は触らない）
Phase 5 公開前    受け口・計測・数字の裏付け・一覧登録・本番URL実機確認
```

### Phase 0 — 基準（Design System）を持つ

既にその組織／プロジェクトの Design System（tokens＋ゲート）があれば**読んで終わり**。無ければ作る。

1. 参照を2系統で選ぶ。
   - **同商材**（同じ商材・同じCV・同じ客層）4本以上。「売れる構成」の参考。見た目の手本としては平凡なことが多い
   - **見た目の手本**（デザインギャラリーの上位）3本。「いいとされる側にしかないもの」を取る
2. 実測する（Playwright または実ブラウザの DevTools。ページ要約は色を誤答するので使わない）。
   PC 1280〜1440 とスマホ 390。測る項目: 型スケール（h1/h2/h3/本文/注記の size・line-height・weight）／
   余白（セクション間・コンテナ幅）／本文1行の字数／面（セクション数・背景色の切替回数・角丸・罫線）／
   画像（FV の画像面積比・実例の枚数）／CTA（高さ・色・回数・追従の有無）／色（地・本文・見出し・アクセントとコントラスト比）
3. 表にして「**N本中N本に共通する値**」だけ抜く。差がある項目（CTA の角丸・画像面積など）は「案ごとに選ぶ」に分類する。
4. 「見た目の手本」と「同商材」の差を言葉にする（例: 1画面1メッセージ／余白2倍／画像は実物で面積50%以上／最大文字は本文の5倍／書体に投資）。
   **この差が自分の成果物を同業より上に見せる唯一の手段**なので、tokens に反映する。
5. tokens を1つ決める（和文1書体・本文色は真っ黒にしない・CTA 1色・追従CTA・容器幅・余白の段）。
   色と角丸はブランドで決める。**`tokens.css` 冒頭に根拠（参照と実測値）をコメントで残す**。
6. 合格条件を数値で持つ（§デザインゲート 8項目）。禁止事項も一緒に書く。

出力: 実測表（reports/ か docs/）＋ tokens ＋ ゲート。ここまで来るまで見た目を1行も書かない。

### Phase 1 — 候補ギャラリー（多数→撮影→採点→絞る）

1. 同じ tokens・同じ素材で、**雰囲気・構図・写真の扱い**を変えた候補を実HTMLで **7〜10本** 作る。
   1本 = 単一 HTML（FV＋主要2〜3面で足りる）。共通の `base.css` に tokens を置き、候補ごとに差分だけ書く。
   候補に「中の実物」（製品画面・デモ・サンプル）を入れるなら、§絶対ルール 7 を先に処理する。
2. Playwright で全候補を撮影（PC 1440 / SP 390、全長）。`shots/` に保存。
3. 自己採点: **「パッと見で頼みたくなるか」1〜10** ＋理由1行。下位 3割を落とす（落とした候補はスクショだけ残す）。
4. 残った候補を**比較ページ1枚**（Artifact かローカル HTML）に並べ、人に「残す／落とす」を決めてもらう。
   並べ方は同じ幅・同じ順（PC と SP を縦に）。採点と理由を添える。
5. 人の指摘を受けて 2回目（残った候補の細部・スマホ幅・句読点などの統一）、必要なら 3回目。
   **「3方向」が配置違いになっていたら、雰囲気の軸で作り直す**（例: 職人・本物／楽しい・元気／安心・信頼）。
6. 1本に絞る。落とした候補の良い要素（帯の流れ・チップ切替など）は「取り込みリスト」として実装へ渡す。

実例の数字: 10本→7本（自己採点）→3本（人）→1本。周回3回。1回目に出した「3方向」は配置違いで却下。

出力: `候補ディレクトリ/README.md`（残した方向・落とした理由・比較ページURL）、`shots/`、取り込みリスト。

### Phase 2 — 実装

- **hallmark**（グローバル登録）を Skill ツールで起動して実装する。本命候補を仕様とし、取り込みリストを足す。
- 見出しに句点を付けない。1画面1メッセージ（見出し2行＋短文＋実物1枚）。数字は1画面に1つ。
- 作り込みの**最中**に撮影して見る。完成後に verify を回すのでは遅い（列潰れ・追従CTAが本文を覆う事故は見ないと気づかない）。
- 候補と実装のスクショを並べ、候補から落ちた点を自分で挙げる。

### Phase 3 — デザインゲート（合否）

8項目を 0/1 で採点し、**6点以上で合格**。不合格項目は直して再採点。PR 本文に採点表を貼る。

| # | 項目 | 判定の仕方 |
|---|---|---|
| 1 | 型スケールが3段以内で一貫している（見出し／本文／注記） | 使用 font-size を列挙して段数を数える |
| 2 | 余白で区切り、罫線・枠で区切っていない | セクション境界の実装を見る |
| 3 | 本文の行長が 25〜45字（日本語） | 本文幅 ÷ font-size |
| 4 | 文字と背景のコントラスト比 4.5:1 以上 | 実測（本文・CTA・帯の上の文字） |
| 5 | 図版・写真の置き場が決まっている（文字だけの面が無い） | 面ごとに画像/図解の有無を表にする |
| 6 | 中央揃えは見出し1箇所以内 | `text-align:center` の箇所数 |
| 7 | 同形カードの横並びは1箇所以内 | 同じ形のカード列の数 |
| 8 | 書体は2種類以内（見出し／本文） | `font-family` の実値 |

加えて **「パッと見で頼みたくなるか」1〜10 ＋理由1行**、**旧版／候補との比較スクショ**（PC 1440・SP 390）を貼る。

禁止（1つでもあれば不合格扱い）: 中央揃えの多用／同形角丸カードの横並び／グラデ帯の見出し／文字だけの面。

採点表テンプレ:

```md
## デザインゲート（<対象> / <日付>）
| # | 項目 | 点 | 根拠 |
|---|---|---|---|
| 1 | 型スケール3段以内 | 1 | 88/40/22/16/13 → 見出し2段＋本文＋注記 |
| … | | | |
| 合計 | | 7/8 | 未達: 5（料金面が文字のみ） |
パッと見で頼みたくなるか: 8/10 — FV に実物3枚、CTA 1色、余白が参照の2倍
比較: shots/compare/{old,new}-{pc,sp}.png
```

### Phase 4 — 訴求レビュー（見た目は触らない）

見た目が合格しても、売れるかは別。次の3問を**初めて見る人の目**で答える。1つでも No なら面の順序と文言を組み直す。

1. **3秒で何を売っているか分かるか**（業種名・商材名が最初の画面にあるか。雰囲気の名前やコンセプト語だけになっていないか）
2. **読み手の得が最初の画面にあるか**（「無料で」「作る前に」など、読み手側の言葉で）
3. **実物に触れられるか**（デモ・サンプル・画面が開けるか。スクショだけで終わっていないか）

組み直しの型（読み手の判断順）: 何を売るか＋得＋実物 → 失敗（読み手の経験）→ 約束 → 実物（触れる）→ 仕組み → 料金（含まれるもの）→ 向く／向かない → FAQ → 最後のCTA。
制作側の語彙（雰囲気の型名・構図型名・内部の工程名）は訴求に出さない。

実例: 2026-10-25 自社LP。「デザインは良くなったが TOP で HP/LP 制作と分からない。『職人・楽しい・安心』は何の訴求か不明（制作側の語彙だった）。触れるデモが見当たらない」→ 見た目を変えずに面を組み直し、3案を触れるデモにリンクした。

### Phase 5 — 公開前チェック

- 受け口（フォーム・問い合わせ）が**実際に届く**ことを本番相当で1回通す。届かないまま公開しない
- 計測パラメータ（流入元）がリンクに引き継がれる
- 裏付けの無い数字は「目安」表記にするか `dummy` フラグで機械検出できる状態にする（景表法）。実在しない「お客様の声」は出さない
- 成果物の一覧（library・HANDOFF 等）に登録する。登録されていないものは人には見えない
- 本番URLを実ブラウザで開き、PC/SP・console を確認する（動作の手順は [[verification-loop]]）

## 出力（Receipt に残すもの）

- 実測表と tokens（Phase 0）／候補 README・shots・比較ページURL（Phase 1）
- 採点表（8項目＋パッと見＋比較スクショ）を PR 本文に（Phase 3）
- 訴求3問の答えと組み直した面の順序（Phase 4）
- 公開URL・一覧登録URL（Phase 5）

## 実行モデルティア

推奨ティア: **deep**（候補の採点・落とす判断・訴求の3問は推論力に依存する）。
`standard` で動かす場合は、Phase 1 の候補数を5本に減らし、採点は8項目ゲートの機械的な判定だけに絞り、
「パッと見」採点と訴求レビューは人に委ねる。具体的なモデル名は `.skills/MODEL-TIERS.md`。
