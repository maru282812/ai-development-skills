# Purpose

**「どう見せるか」がまだ決まっていない UI を、実装する前に見比べさせる。**

このスキルが解く問題は1つだけ。見た目の相談に対して、いきなり実装して1案だけ見せてしまい、
気に入らなければ作り直し、という往復を潰す。**先に案を並べる。選ばれてから作る。**

# 絶対ルール

1. **プロジェクトのコードを1行も変更しない。** 触っていいのは Artifact とプレビュー出力先だけ。
   `src/` `app/` `components/` `lib/` などへの Write / Edit は、案の選定後も**このスキルの中では**行わない。
2. **勝手に1案に絞らない。** 3〜5案を必ず並べる。「これがいいと思います」で1案だけ出すのは違反。
   推しがあるなら、並べた上で最後に理由付きで推す。
3. **選定ゲートで必ず止まる。** プレビューを出したら「どれにしますか」で停止する。
   ユーザーが案を選んでも、このスキルは[適用ブリーフ](#5-適用ブリーフ選定後停止)を出して終わる。
4. **見た目を捏造しない。** 案はプロジェクト実物のトークン・既存コンポーネントの上に載せる。
   参照できない場合は「素の見た目で作った」と明示する（[Design Context の抽出](#2-design-context-の抽出)）。
5. **色だけに意味を載せない。** ランク・状態・重要度を色だけで表現する案しか無い、という並びにしない
   （必ず1案以上、文字/形/位置でも判別できる案を含める）。

# When To Use

- 見た目・表現方法に迷っていて、言葉で説明されてもピンと来ない
- 「ランクをカードでどう出すか」「バッジか枠線かリボンか」のような**表現の選択**をしたい
- 配色 / レイアウト / 情報の並び順 / 密度 の代替案を見比べたい
- 実装前に関係者と見た目の合意を取りたい

使わない場面:

- 要件から**必要な画面そのもの**を洗い出す → [[screen-design-architect]]
- **既に実装済み**の画面の導線・使い勝手を診断する → [[ui-ux-review]]
- 見た目が既に決まっていて実装するだけ → [[implementation-planner]] / 通常フロー
- **外部の参照サイトを探すところから**方向性を決める（新規制作・全面リデザインの提案フェーズ）
  → [[design-reference-scout]]（ギャラリーを複数軸で検索し3軸で提案する担当。
  本スキルは**プロジェクト実物のトークン上**で見た目を並べる担当なので、
  「参考サイトを探して」「作り直すとしたらどうする」で始まる依頼はあちらへ）

# Procedure

## 1. 対象とスコープの確定

まず「何の案を並べるのか」を1文にする。曖昧なまま案を作らない。

- **対象の粒度**: UI要素（バッジ・ボタン）/ コンポーネント1つ（カード・行）/ 画面1枚（一覧・詳細）
- **可変にする軸**: 何を変えた案が見たいのか（表現方法 / 配色 / レイアウト / 密度 / 階層）
- **固定するもの**: 変えてはいけない要素（既存の配色、コンポーネント構造、ブランド色 など）

1文で言えない場合だけ、表で確認する（一問一答はしない）。

| 確認項目 | 候補 | 回答 |
|---|---|---|
| 対象 | 要素 / コンポーネント / 画面 | |
| 変えたい軸 | 表現 / 配色 / レイアウト / 密度 | |
| 変えてほしくないもの | | |
| デバイス | PC / スマホ / 両方 | |

## 2. Design Context の抽出

**案がプロジェクトから浮かないように、実物を吸ってから作る。** ここを飛ばすと「きれいだが実装したら別物」になる。

| 拾うもの | 探す場所（無ければ次へ） |
|---|---|
| 配色トークン | `tailwind.config.*` の `theme.extend.colors` / `app/globals.css` の CSS変数 / `styles/` |
| タイポ・角丸・影 | 同上（`fontFamily` / `borderRadius` / `boxShadow`） |
| 対象コンポーネントの現状マークアップ | `components/**` `app/**` を Grep（対象名・クラス名で） |
| 既存の類似表現 | 同種の Badge / Card / Table コンポーネント |
| 表示する実データの形 | 型定義・`lib/**` の変換関数・seed / モックデータ |

- 拾ったトークンは**そのまま使う**。プレビュー内で新しい色を発明するのは、それ自体が案の論点になっているときだけ。
- Tailwind を使っているプロジェクトなら、プレビューも同じクラス名で書く（実装時にそのまま移植できる）。
- **何も拾えなかった場合**は「プロジェクトのデザイントークンが見つからなかったので素の見た目で作った」と
  プレビュー冒頭と回答の両方に明記する。黙って一般的な見た目で作らない。

## 3. 案の設計（3〜5案）

案は「なんとなく違う5枚」ではなく、**軸をずらした5枚**にする。各案は1行で「何が違うのか」が言えること。

### 案出しのルール

- **軸を散らす**: 全案が「色違い」にならないようにする。表現の置き場所（バッジ / 枠線 / 背景 / リボン / アイコン）、
  情報の階層（目立たせる / 溶け込ませる）、密度 のように**別の次元**で振る。
- **主張の強さで並べる**: 控えめ → 強い の順に並べると見比べやすい。各案に強さ指標（●●●○○）を付ける。
- **両端を必ず入れる**: 「ほぼ現状維持の案」と「はっきり主張する案」を必ず1つずつ入れる。中庸だけ5案は情報量ゼロ。
- **アクセシビリティの逃げ道を残す**: 色だけに意味を載せる案しか無い並びにしない（[絶対ルール](#絶対ルール) 5）。

### 各案に必ず付ける情報

| 項目 | 内容 |
|---|---|
| 案ラベル | 案A / 案B …（会話で「案Cで」と指せるように） |
| 案名 | 「枠線＋右上のコーナーリボン」のように**手法が分かる**名前 |
| 説明 | 2文以内。何を狙った案か、副次的な利点は何か |
| 主張の強さ | ●●●○○ |

## 4. プレビューの生成

### レイアウト規約

**同じデータ・同じ並び・同じ幅**で全案を縦積みする。案ごとにデータが違うと比較にならない。

```text
[ヘッダー]  <対象名> デザイン <n>案  ／ 生成日 ／ Design Context の出所
  ├ 案A  <案名>            主張の強さ ●●○○○   説明
  │   [ 同一データ 4件を横並び ]
  ├ 案B  <案名>            主張の強さ ●●●○○   説明
  │   [ 同一データ 4件を横並び ]
  … 案C / 案D / 案E
[選ぶときの観点]  用途別の推し ／ エッジケースの挙動 ／ 決定後の適用先
```

### サンプルデータの規約

サンプル4件のうち、**必ず1件はエッジケース**にする（未設定 / 空 / 極端に長い文字列 / 権限なし）。
きれいなデータ4件だけで並べると、選んだあとに「未設定のとき崩れる」で作り直しになる。

- 実データの形が分かっているなら、それに沿ったダミーを作る（実データそのものは持ち込まない）
- 個人情報・実顧客名・実在の金額は使わない。ダミー名（山田 太郎 等）にする

### 末尾の「選ぶときの観点」

プレビューの最後に必ず置く。ここが選定の判断材料になる。

- 用途別の推し（例:「一覧で見比べさせたいなら案A・案B、個人を読ませたいなら案C」）
- エッジケースの挙動（例:「未設定の社員はどの案でも無色のカードに落ちる」）
- 方針上の制約（例:「色だけに意味を載せない方針なら案B・案Eが安全」）
- 決定後の適用先（例:「`lib/rank.ts` の `RANK_TONE` に card 用クラスを足すだけ」）

### 出力先

**Artifact を優先し、使えなければローカルHTMLに落とす。**

1. **Artifact（既定）**
   - 書く前に必ず `artifact-design` スキルを読む（デザイン投資量のキャリブレーション）。
   - ライト/ダーク両対応、外部CDN禁止（CSSは全てインライン）、横スクロールさせない。
   - Tailwind を使っているプロジェクトでも Artifact は外部CDN不可なので、
     **クラス名はコメントで併記しつつ、実際のスタイルはインラインCSSで再現**する
     （実装時にクラス名がそのまま移植できるようにするため）。
   - `favicon` は案の対象に合ったものを1つ選び、同じ対象の再出力では変えない。
2. **ローカルHTML（Artifact が使えない環境 / 機密案件 / ユーザー指定時）**
   - 出力先: `<project>/.design-preview/<YYYY-MM-DD>-<slug>.html`
   - `.gitignore` に `.design-preview/` が無ければ追記する（プレビューはコミット対象外）
   - 生成後、ファイルパスを提示する（開くかどうかはユーザーに任せる）

どちらで出したかは回答に明記する。

## 5. 適用ブリーフ（選定後・停止）

ユーザーが案を選んだら、**実装せずに**次を出して停止する。

```md
## 採用: 案<X> <案名>

### 適用先
| ファイル | 変更内容 |
|---|---|
| <path> | <何をどう足す/差し替えるか> |

### 追加が必要なトークン
- <色 / クラス / CSS変数>（既存で足りるなら「不要」）

### 影響範囲
- 同じコンポーネントを使っている箇所: <...>
- 崩れうるケース: <エッジケース>

### 未確定
- <残っている論点>

→ 実装は [[implementation-planner]] へ。実装しますか？
```

**この提案を出した時点でこのスキルは終わり。** ユーザーが「実装して」と言ったら、
このスキルを抜けて [[implementation-planner]] または通常の実装フローに入る。

# 反復

「案Cの色を案Aにしたい」「もう2案足して」のようなフィードバックは、
**プレビューを再生成**して応じる（同じ Artifact URL / 同じファイルパスに上書き更新する）。

- 元の案ラベルは維持する（案C は最後まで案C。番号を振り直すと会話が壊れる）
- 派生は 案C-2 のように枝番にする
- 変更点は回答で1行にまとめる（「案C の枠線色を案A のトークンに変更、案F・案G を追加」）

# セルフチェック

- プロジェクトのコードを1行も変更していないか
- Design Context を実物から抽出したか（できなかったなら明記したか）
- 3案以上あるか / 全案が「色違い」になっていないか
- 各案に 案ラベル・案名・説明・主張の強さ が付いているか
- 全案が同じデータ・同じ並びで比較できるか
- サンプルにエッジケース（未設定 / 空 / 長文）を1件以上入れたか
- 色だけに意味を載せない案が1つ以上あるか
- 「選ぶときの観点」を末尾に置いたか（適用先まで書いたか）
- 選定ゲートで止まったか / 勝手に実装に進んでいないか
- Artifact / ローカル どちらで出したか回答に書いたか

# 実行モデルティア

推奨ティア: **deep**（「どの軸で案を振るか」「何を捨てるか」の判断が出力の質を決めるため）。
最上位推論クラスのモデルが使えない環境でも中止しない。代わりに劣化運転として、
案の軸をユーザーに先に確認してから生成し、案数を絞って1サイクルを短くし、
推しを1案に断定せず用途別の候補として提示すること。
具体的なモデル名はここに書かない（対応表は `.skills/MODEL-TIERS.md`）。
