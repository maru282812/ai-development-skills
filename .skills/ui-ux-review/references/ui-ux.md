## 1. 画面状態チェックリスト

すべてのデータ表示画面で4状態を確認する。

### 空状態(0件)

- [ ] 空白やテーブルヘッダだけにならず、「データがない理由」と「次にすべきこと」を表示している
- [ ] 作成系のCTA(「最初の〇〇を作成」)を空状態に置いている
- [ ] 検索・フィルタ結果の0件と、本当にデータがない0件で文言を分けている

### ローディング

- [ ] スピナーまたはスケルトンがある(真っ白の時間がない)
- [ ] 読み込み完了時のレイアウトシフトが小さい(スケルトンを実寸に近づける)
- [ ] 送信中はボタンを disabled にし、処理中であることを示す(二重送信防止と兼ねる)

### エラー

- [ ] 失敗がユーザーに見える(console だけに出て画面は正常風、になっていない)
- [ ] エラー文言が「何が起きたか + どうすればよいか」を含む
- [ ] リトライ手段(再読み込みボタン等)がある

### 正常

- [ ] 大量データ(100件超)でページネーション・仮想化等の対策がある
- [ ] 長いテキスト・長い名前で崩れない(truncate / 折り返し)

## 2. フォームチェックリスト

- [ ] 項目数は必要最小限か(後から埋められる項目を初回登録に混ぜていないか)
- [ ] 必須/任意が見た目で区別できる
- [ ] 項目の順序がユーザーの思考順(重要・確実に書けるものが先)
- [ ] 適切な入力タイプ(`type=email/tel/number`、`inputmode`)でスマホのキーボードが切り替わる
- [ ] バリデーションのタイミング: 入力中に怒らない(blur または submit 時)。submit 後はエラー項目までスクロール
- [ ] エラーは項目の近くに表示(画面上部だけに出さない)
- [ ] 送信ボタンの文言が動作を表す(「送信」より「メンバーを招待」)
- [ ] 送信中の disabled + ローディング表示
- [ ] 成功後のフィードバック(トースト・遷移)があり、二度押し・迷子にならない
- [ ] 離脱時の入力消失対策(確認ダイアログ、または下書き保存)— 長いフォームのみ

## 3. 管理画面・スマホ・LIFF の定石

### 管理画面(一覧 / 詳細 / 編集)

- 一覧: 「探す」機能が主目的。検索・フィルタ・ソートを上部に、行クリックで詳細へ。
  状態(有効/無効等)はバッジで視覚化。よく使う操作(編集等)は行内に出してよいが、破壊的操作はメニューに隠す
- 詳細: 関連情報への導線(このユーザーの注文一覧へ、等)を張る。編集とは分けるか、明確な編集モードを持つ
- 編集: 保存・キャンセルを固定位置に。保存成功は明確にフィードバック
- 削除等の破壊的操作: 確認ダイアログ + 対象名の表示(「〇〇を削除しますか」)。
  取り返しがつかないものは名前の再入力等のガードを検討
- CTA は1画面1主ボタン。primary スタイルを複数並べない

### スマホ

- タップ領域は 44px 四方を目安(小さいアイコンボタンの隣接配置を避ける)
- テーブルはカード表示への切り替え、または重要列のみ表示 + 詳細へ誘導(横スクロールは最終手段)
- 固定フッターのCTAはキーボード表示時の挙動を確認
- ホバー前提のUI(ツールチップ、hoverで出るメニュー)はスマホで使えない — タップで代替
- モーダルの多段重ねを避ける(スマホでは全画面シートが扱いやすい)

### LIFF 固有

- LINEアプリ内ブラウザは画面が狭い(ヘッダ分)。1画面1タスクに絞る
- ログインは LIFF の自動ログインに任せ、メール登録フォームを挟まない
- 外部リンクは LIFF 外に出る(戻れない場合がある)ことを意識して配置
- `liff.init` 完了までのローディング表示を必ず置く(白画面で止まったように見える)
- 閉じる動作(`liff.closeWindow`)を完了画面に置くとトーク画面に自然に戻れる

### 文言の原則

- ユーザーの言葉で書く: 「不正な値です」→「メールアドレスの形式で入力してください」
- エラーは「何が起きた + どうすればよい」をセットで
- ボタンは名詞でなく動詞(「OK」より「保存する」「削除する」)
- 確認ダイアログは肯定/否定ボタンに動作を書く(「はい/いいえ」より「削除する/キャンセル」)
