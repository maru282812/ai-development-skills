# データ発見: CLEAN TOILET(仮)

更新日: 2026-06-21

## 目的

CLEAN TOILET(仮) は、トイレの場所だけでなく「安心して行けるか」を判断するためのデータを扱う。
駅構内図、駅設備、商業施設トイレ情報、号車情報は公式情報を正とし、ユーザー投稿は現地補足、更新提案、実体験情報として重ねる。
初期リリースの対象国は日本のみとする。ただし将来の海外対応で作り直しにならないように、国、地域、言語、通貨、タイムゾーン、データ信頼度、公式ソース種別を扱える余地は残す。
初期対象エリアは関東を主対象にし、大阪・福岡は空港/主要駅ハブに絞って初期拡張対象にする。

## データ正本の優先順位

| 優先順位 | データ種別 | 扱い |
|---:|---|---|
| 1 | 鉄道事業者、商業施設、自治体、施設運営者の公式情報 | 正本。位置、設備、利用条件、号車案内などの基準にする |
| 2 | 施設/店舗/テナントオーナーの確認済み提供情報 | 公式扱い。ただし申請者確認と運営承認を通す |
| 3 | 運営者が公式情報または現地確認で登録した情報 | 準公式。公式URL、確認日、確認者を残す |
| 4 | ログイン済みユーザー投稿 | 実体験、写真ステップ、混雑、清潔度、迷いやすさの補足。公式を直接上書きしない |
| 5 | ゲストの軽量状態投稿 | 一時的な満室、閉鎖、汚れなどの速報。信頼スコア、称号、SNSカードには反映しない |
| 6 | Google Places、OpenStreetMap、GTFS等の外部候補データ | 初期候補、重複照合、海外調査の補助。公開前に信頼度を付ける |

## 公式/手入力/投稿の分担

| 対象 | 公式を正にする範囲 | 手入力/運営入力の範囲 | 投稿で扱う範囲 |
|---|---|---|---|
| 駅構内図 | 公式サイト、公式PDF、駅掲示情報を正本にする | 公式情報を階層、改札、出口、ホーム、トイレ単位に整理する | 迷いやすい場所、現地の目印、工事中、案内板写真を補足 |
| 駅設備 | 公式のトイレ、エレベーター、多目的、改札内外、営業時間を正本にする | 駅攻略ページに使える形へ整形する | 清潔度、混雑、実際に入れるか、閉鎖中などを補足 |
| 商業施設トイレ | 施設公式マップ、施設オーナー情報を正本にする | フロア、店舗近く、入口、利用条件を整理する | たどり着きやすさ、混雑、雰囲気、写真ステップを補足 |
| 号車情報 | 鉄道事業者の公式案内があれば正本にする | 路線、方面、改札、ホーム、出口との関係を整理する | 実体験として「この号車が近かった」を補足。公式化は運営確認後 |
| トイレ状態 | 公式の恒久情報は正本にする | 故障、閉鎖、工事などを管理する | 満室、汚れ、怖かった、使えなかった等の鮮度が必要な情報を補足 |

## 問い合わせ・回答ナレッジ

問い合わせはメール、フォーム、管理画面で受け付ける。
AIは問い合わせの分類、優先度付け、類似回答検索、返信下書きを行う。
人間またはAIが作成した回答は、運営が確認したうえでナレッジとして蓄積し、次回以降の回答候補に使う。

| データ | 保存する内容 | 再利用方針 |
|---|---|---|
| 問い合わせ本文 | 送信者、連絡先、対象投稿/施設、カテゴリ、本文、添付、受信日時 | 個人情報を含むため、そのまま回答候補には使わない |
| AI分類結果 | カテゴリ、緊急度、推奨担当、類似問い合わせ、返信下書き | 人間確認前は内部補助に限定する |
| 最終回答 | 実際に送った回答、回答者、送信日時、根拠、承認者 | 個人情報や個別条件を除いた形でナレッジ化する |
| ナレッジ | 質問要約、標準回答、対象カテゴリ、公開可否、再利用可否、最終確認日 | 承認済みのものだけAI回答候補に使う |

自動再利用しないもの:
- 個人情報を含む回答
- 個別の契約条件、価格交渉、返金、法務判断を含む回答
- 投稿者BAN、削除、通報者保護に関わる回答
- 運営者が未承認のAI下書き

## 同意ログ

ユーザー承認は、規約同意、プライバシーポリシー同意、位置情報利用、投稿規約、写真/撮影ガイドライン、トイレ内写真確認、SNS共有、スポンサー付きカード、支援者名掲載などを分けて扱う。

| データ | 保存する内容 | 再利用方針 |
|---|---|---|
| 同意種別 | terms, privacy, location_rationale, post_guideline, photo_guideline, restroom_photo_notice, sns_share, sponsored_share_card, supporter_listing 等 | 同意状態の判定に使う |
| 規約/文書バージョン | 同意した文書ID、バージョン、URL | 規約改定時の再同意判定に使う |
| 同意日時 | 同意した日時 | 証跡として保存 |
| 対象ユーザー | user_id または匿名閲覧時の端末識別子 | 個人情報として扱い、最小限にする |
| 同意画面 | どの画面で同意したか | 問い合わせ・監査時の確認に使う |
| 撤回状態 | 撤回日時、撤回対象 | 支援者名掲載や通知等の停止に使う |

## 支援者データ

クラウドファンディング支援者情報は、取込用の原本データと、アプリで使う支援者権利データを分ける。

| データ | 保存する内容 | 保持/削除方針 |
|---|---|---|
| 支援者取込CSV | 支援者ID、リターン種別、支援ステータス、連絡用メール、支援日時、管理メモ | 取込確認後90日以内に削除またはアクセス制限付きアーカイブ。ローカル端末に残さない |
| 支援者権利データ | supporter_id、return_type、invite_code、claim_status、linked_user_id、fulfillment_status | リターン提供と問い合わせ対応に必要な期間だけ保持 |
| 表示名/掲載同意 | 任意の表示名、掲載範囲、同意日時、同意文書バージョン、撤回状態 | 掲載中は保持。削除依頼後は公開停止し、監査用の最小ログだけ残す |
| 店舗/施設掲載情報 | 店舗/施設名、所在地、公式URL、担当者連絡先、掲載内容、掲載同意 | 掲載期間中と問い合わせ対応に必要な期間だけ保持 |
| スポンサー掲載情報 | 企業/団体名、担当者連絡先、掲載プラン、掲載期間、素材、PR表記、請求/提供状態 | 契約・請求・掲載履歴として管理し、公開用データと請求用データを分ける |
| 削除/変更依頼 | 依頼者、対象データ、依頼日時、対応状態、対応者、対応日時 | 対応履歴として保持し、回答ナレッジには個人情報を含めない |

アプリ連携:
- 支援者にはメールリンクまたは支援者コードを送る
- アプリでログイン後、支援者コードまたはメールリンクでアカウントに紐づける
- 紐づけ時に、利用規約、プライバシーポリシー、支援者連携、名前掲載/バッジ表示の同意を確認する
- 支援者コードは平文保存せず、検証用にはハッシュ化またはワンタイムトークン化する
- 連携後も、名前掲載、バッジ表示、店舗/施設掲載、スポンサー掲載は個別に表示/非表示を管理できるようにする

## 法務/税務レビュー記録

公開前レビューの証跡として、レビュー対象、版、指摘、対応状況を残す。
レビュー担当者の個人情報は、契約/請求/連絡に必要な範囲に限定する。

| データ | 保存する内容 | 保持/削除方針 |
|---|---|---|
| レビュー対象 | 文書名、画面名、URL、版、更新日 | 公開版の根拠として保持 |
| レビュー依頼 | 依頼日、依頼先種別、対象範囲、質問事項 | 公開前チェックの証跡として保持 |
| 指摘事項 | 指摘内容、重要度、対象箇所、担当者、対応方針、再確認要否 | 高重要度の指摘が残っている場合は公開しない |
| 対応結果 | 修正内容、修正版、完了日、再レビュー結果、未解決リスク | 公開判断の記録として保持 |

## 海外データ精度の扱い

MVPでは海外データを収集・公開しない。
海外対応は将来候補であり、初期は日本国内の公式情報、投稿、運営確認に集中する。

海外では、国、都市、データ種別ごとに精度が大きく変わる。
そのため、全世界を同じ品質で一括展開せず、国・都市・データ種別ごとに信頼度を持つ。

| 信頼度 | 条件 | 表示/運用 |
|---|---|---|
| A: 公式/提携 | 公式データ、施設/交通事業者提供、利用許諾がある | 公式情報として表示できる |
| B: 実用候補 | GTFS/GTFS Pathways、Google Places、OpenStreetMap、現地投稿が複数一致する | 確認済み候補として表示する |
| C: 未確認候補 | 外部データまたは投稿のみで、公式確認がない | 「未確認」または「投稿情報」と明示する |
| D: 不十分 | 外部データ密度が低く、現地投稿も少ない | 対象エリアにしない、または投稿募集対象に留める |

調査メモ:
- GTFSは駅、ホーム、出入口、構内ノード、乗車位置などの構造を表現できるが、各事業者が提供している範囲に依存し、トイレ詳細が必ず入るわけではない。
- Google Placesには `public_bathroom` の種別があるが、駅構内の階層、個室数、改札内外、導線まで保証するものではない。
- OpenStreetMapには `amenity=toilets` や `toilets:*` のタグがあり、施設内トイレの公開可否も表現できる。ただし地域差とタグのばらつきがあるため、初期候補や照合には使えるが正本にはしない。

## データ量対策

初期から日本全国/全世界の全量取り込みをしない。
対象駅、路線、エリア単位で段階投入し、MVPでは日本国内の「使われる可能性が高い場所」から整理する。
初期データ投入は、関東の主要駅、空港、駅周辺を主対象にする。関東以外は大阪・福岡の空港/主要駅ハブに限定し、その他地域は投稿募集候補または未整備エリアとして扱う。

| 課題 | 方針 |
|---|---|
| 駅・商業施設データが多い | 優先エリア、主要駅、クラウドファンディング支援者の利用地域から段階投入する |
| 外部データ候補が多い | 公開テーブルに直接入れず、候補ステージングに入れて重複統合と信頼度判定を行う |
| 写真ステップが増える | 1ルートあたりの枚数上限を設け、圧縮後画像を保存する。古い低評価/低利用画像はアーカイブ対象にする |
| 構内図画像の権利リスク | 公式構内図画像は原則保存しない。公式URL、確認日、要約された構造データを保持する |
| 検索対象が増える | 現在地、駅名、表示範囲、近傍検索を中心にし、全件ロードしない |
| 海外展開で国ごとに差が出る | 国/都市単位で信頼度、利用ソース、確認日、対象外理由を持つ |
| 同一施設内の重複 | 建物ID、フロア、トイレグループ、種別、座標、ソースIDで重複判定する |

## MVPで決めること

- 公式情報を正本とし、投稿は補足として扱う
- 初期リリース対象国は日本のみとする
- 初期対象エリアは関東を主対象にし、大阪・福岡は空港/主要駅ハブに絞る
- 未確認情報には確認状態を表示する
- 公式URL、確認日、取得元、利用許諾状態を持つ
- 日本全国/全世界全量ではなく、日本国内の初期対象エリアから段階投入する
- 公式構内図画像や商業施設マップは、権利確認なしに保存しない
- 写真/動画のうち、MVPでは写真のみ扱い、動画は扱わない
